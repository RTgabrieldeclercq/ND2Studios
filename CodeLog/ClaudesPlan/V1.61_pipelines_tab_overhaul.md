# V1.61+ — Pipelines Tab Overhaul (master plan, phased)

## Goal

A ground-up overhaul of the **Pipelines** page turning the current two
sub-tab (Processing / Analysis) node editor into a single unified,
file-aware, auto-arranging graph editor with a per-node "point-of-view"
(POV) multi-viewer on the right. Fourteen interlocking requirements (R1–R14,
verbatim from the user brief) delivered **phased across versions** (V1.61 →
V1.64), each independently shippable and verifiable — mirroring how the
Pipelines tab was originally built (V1.45.x).

## Confirmed decisions (from the user)

1. **Phased delivery** across versions in dependency order.
2. **POV = a dedicated dropdown** on the right side that shows **cached
   results only** (never auto-launches heavy compute). It is a *separate*
   concept from today's sticky double-click "previewed node."
3. **One input node per Import panel**, named by the file **basename**
   (editable). Closing a file **disables** (greys) its node but keeps it and
   its edges so the pipeline structure survives (`panel ≠ file`: a reconstruct
   chain is one panel ⇒ one node).
4. **Unified end-to-end Run** — one Run button executes the whole graph per
   input file (processing → analysis → results). Delivered as an
   *orchestration layer* over the existing two engines (recipe linearization +
   `GraphRunner`), not a from-scratch executor rewrite.

## Decisions taken here (revisit if you disagree)

- **R8 channel model:** channels attach to the input-node body and **subsume**
  the standalone `channel:{name}` PILL source nodes *for file inputs*. The PILL
  spec is retained for **backward-compatible load only** (saved graphs with
  channel pills still open). New graphs never create pills.
- **R13 multi-input rendering:** when 2+ inputs feed one output, render **one
  tab per feeding input** (each showing that input's overlay + results), per
  the brief's "the tab should show up twice." Not a single composited overlay.
- **R7 label groups persist** in `.nd2s_pipeline.json` (schema bump), and
  **R6 auto-arrange keeps group members contiguous** (a group is laid out as a
  movable cluster).
- **R5 multi-select:** plain empty-area drag = **pan**; **Ctrl/Shift-drag**
  preserves rubber-band marquee select; the **lasso** (R7) is the primary
  region-select gesture.
- **R6 spacing:** "minimal spacing" is derived from real `NodeItem` size with a
  fixed readability floor (layer gap + sibling gap constants), not a magic px.
- **R1 merge shape:** all nodes live in **one `GraphSlice`** rendered in one
  scene; `node.stage` is retained purely for **execution dispatch** (processing
  = enhancement recipe, analysis = pipeline, results = measurements). The
  Processing-OUTPUT→Analysis-INPUT `Bridge` collapses to a direct edge on
  migration.

## Phase plan (dependency-ordered)

Critical path: **R1 → R3 → R8 → R6**, in parallel with
**R1 → per-node result registry → R12/R13 → R11/R14**.

### Phase 1 — V1.61: One tab + navigation + submenu + rename
*Merge the editor surface and fix core interaction. No result-system changes.*

Split into two sub-passes so the risky merge is verified in isolation:

**Phase 1a — DONE (R2/R4/R5), verified offscreen.** The three contained,
independent UX requirements. See CHANGELOG "V1.61 Phase 1a".
- **R2** ✅ Per-category submenu right-click Add menu
  (`node_scene._CATEGORY_MENU_ORDER`/`contextMenuEvent`).
- **R5** ✅ Click-drag pan on empty canvas; Ctrl/Shift-drag marquee; tool-aware
  (`_BoardView` `_panning`/`_tool_active`).
- **R4** ✅ Double-click inline rename for INPUT **and** OUTPUT nodes; commit on
  click-away (`NodeItem._is_renamable`/`mouseDoubleClickEvent`).

**Phase 1b — DONE (R1), the executor-unification merge. Verified headless; needs
interactive validation on a real ND2.**

Implemented exactly as the refined approach below: one scene/slice
(`slice_for` aliases PROCESSING→merged), schema→5 + `io._migrate_v4_to_v5` fold on
load, `self._stage` tracks the previewed node, stage-aware helpers
(`_node_group` / `_stage_output_nodes` / `_stage_input_node`), recipe derivation
reads the merged slice, unified Run (`_on_run` commits the recipe then walks the
analysis graph; the pump passes PROCESSING nodes through; `GraphRunner` starts at
the analysis input), Apply always commits the processing recipe, and the sub-tab
selector is hidden. Verified: self-test; offscreen page; v4 file load; boot.

**Refinement (user request): one connected chain, no bridge nodes.** The
intermediate Processing-OUTPUT and Analysis-INPUT bridge nodes are removed —
there is now a single **universal input** (all loaded files) → processing →
analysis → **output nodes at the ends**. `io._migrate_v4_to_v5` became
`io._migrate_to_connected` (schema → **6**): fold + drop the bridge nodes +
**reconnect** the processing tail (or the universal input) directly to the
analysis heads. Recipe derivation anchors on a new `_processing_tail_node`
(deepest enhancement before analysis) instead of a processing-output node; Run
starts the `GraphRunner` at the universal input. **Base-viewer fix:**
`_select_stage`/`_refresh_active_view` always call `_show_base_image()` (the
viewer was blank because the processing context relied on the debounced pinned
preview); default context kept at Processing so overlay panels don't populate
during `MainWindow` construction. Re-verified: self-test (v4→v6 fold/reconnect +
v6 round-trip); offscreen connected-model page (universal input, no bridges, tail
recipe, Run from universal input); v4 load→connected chain; clean `MainWindow` boot.

**Key finding from the 1b investigation (grounds the whole approach):**
Processing and Analysis are **not joined by a graph edge** — the Processing
OUTPUT node and the Analysis "Processed" INPUT node are linked only through
`record.recipe`. `_on_output_node_created`/`_on_analysis_output_created` register
a `Bridge` that is purely a **name label**; the processed image is handed off by
committing the linearized recipe (`_graph_recipe`→`recipe_for_node`→
`record.recipe`) which the Analysis base reads as a `ProcessedFrameVolume`. So
the two halves run on **two different engines**: Processing = recipe
linearization + `apply_recipe`; Analysis = the `GraphRunner` state machine.

**Consequences for the merge (why it's an executor pass, not a layout change):**
- Folding into one `GraphSlice` is lossless and trivial (no cross-slice edges to
  reconnect — the `_migrate_v4_to_v5` prototype was a straight node/edge move,
  self-tested green, then reverted with the rest of the 1b spike).
- But one runnable scene means: the `GraphRunner` must **pass through**
  enhancement (PROCESSING-stage) nodes (they have no run handler — today they're
  a recipe, not a Run step); `input_node()` / channel-source-pill roots / the
  Run start must become **stage-aware** (the merged slice has two input nodes and
  two pill columns in two disconnected components); and `_graph_recipe` /
  `_graph_channel_recipes` / `_apply_processing` / `_do_processing_preview` /
  bridge counters (~15 execution-critical sites) must filter to PROCESSING-stage
  outputs. Getting any of these subtly wrong yields **wrong scientific results**,
  not just a crash — hence interactive validation on a real file is required.

**Refined approach:** (a) fold to one slice on load via `_migrate_v4_to_v5`
(prototype ready); (b) one scene, aliasing `self._scenes[*]` + `slice_for(*)` to
the merged slice so most of the ~75 stage branches keep working; (c) `self._stage`
**tracks the previewed node** (PROCESSING when an enhancement node is previewed,
else ANALYSIS) so per-stage preview/overlay dispatch works without per-branch
edits; (d) add stage-aware helpers (`_proc_output_nodes` / `_analysis_input_node`)
and make the Run pump **pass through** PROCESSING-stage nodes (mark done, don't
execute); (e) **unified Run** = commit the processing recipe, then `GraphRunner`
the analysis walk. Bump merged schema to 5 + wire `_migrate_v4_to_v5`.

**Done in the 1b spike (kept):** the pre-existing `schema_version` 3↔4 drift is
fixed (`model.PipelineDoc.schema_version` default → 4, matching
`io.PIPELINE_VERSION`); two stale self-test assertions realigned. Self-test green.
The v5 fold model was prototyped + reverted (tree kept stable).

**Deliverable:** a single navigable scene; nodes colored by category; add via
per-type submenu; pan the canvas; rename input/output nodes. Execution keeps
working: a **unified Run** orchestration wrapper drives the existing
processing-commit then analysis-run over the single DAG (deep engine merge
deferred — but the user sees one Run button, end-to-end).

### Phase 2 — V1.62: Multi-input files + channels on the node body

### Phase 3 — V1.63: Auto-arrange + Label groups + loop routing

### Phase 4 — V1.64: Per-node result registry + POV multi-viewer
*The results/viewer system.*

- **Foundation:** a per-node result registry `Dict[node_id → ResultBundle]`
  populated during Run/preview; forward/backward reachability queries on the
  merged `GraphSlice`.
- **R11** POV dropdown on the right + lazily-built viewers (reuse one
  `MultiAxisViewer` per active POV context; share `MaterializedDataset` by ref).
- **R12** Input-node POV → all reachable downstream results (cached).
- **R13** Output-node POV → feeding input(s) + intervening results; one tab per
  feeding input.
- **R14** POV toggle (input-view ⇄ output-view) → the top-level tab becomes a
  **list of connected nodes**, each a tab containing its result sub-tabs.

**Deliverable:** the full POV viewer system driven by a right-side toggle +
dropdown, showing cached results per node context.

## Phase 1 detail (V1.61)

### R1 — Merge to one scene / one slice
**Files:** `pipeline_graph/model.py`, `pipeline_graph/io.py`,
`pages/pipelines_page.py`, `widgets/node_board/node_scene.py`,
`pipeline_graph/executor.py`.

- **Model:** add `PipelineDoc.merged`-as-truth. All nodes go into **one**
  editing slice. Keep `node.stage` for dispatch. The processing slice is folded
  into the merged slice on migration; `slice_for`/`processing`/`results` kept
  as (possibly empty) back-compat accessors so existing executor/io paths that
  reference them don't break mid-refactor.
- **io v4→v5 migration** (`_migrate_v4_to_v5`): move every `processing` node +
  edge into the merged slice; for each `Bridge` joining a Processing OUTPUT
  node → Analysis INPUT node, delete both bridge endpoint nodes and add a
  **direct structural edge** from the OUTPUT node's upstream producer port to
  the Analysis INPUT node's downstream consumer port (payload IMAGE→IMAGE).
  Bump `PIPELINE_VERSION=5`, `PipelineDoc.schema_version=5`. Loop edges and
  positions preserved. Round-trip + migration covered by the Qt-free self-test.
- **Page:** delete `_build_subtab_selector`; `self._stages` collapses to a
  single merged view. One `NodeScene` whose `action_specs` =
  `enhancement_specs() + merged_action_specs()`. `_select_stage` logic folds
  into a single init; Loop button always available; **Run replaces the
  Apply/Run toggle** (unified Run). Category colors unchanged
  (`_CATEGORY_COLOR`), so processing=cyan / analysis=pink / results=green /
  logic=purple / special=orange / checkpoint=white all coexist.
- **Unified Run orchestration** (`_on_run`): topological walk of the single DAG;
  dispatch each node by `node.stage` — processing nodes linearize + apply a
  recipe (existing `recipe_for_node`/`apply_recipe`), producing the processed
  image that analysis nodes consume; analysis/results/logic/special nodes run
  via the existing `GraphRunner` semantics. Preview unchanged in spirit
  (previewed node still resolves its upstream chain across stage boundaries).
- **Risk:** highest. Executor must resolve an analysis node's upstream
  **processed image** across the (now direct) edge. Mitigation: the migration's
  direct edge preserves the exact producer→consumer relationship the bridge
  encoded, so `recipe_for_node` walking back from an analysis input reaches the
  processing chain and its input node unchanged.

## Cross-cutting notes for later phases

- **Per-node result registry (Phase 4)** is the single biggest data gap; design
  it as `Dict[node_id → ResultBundle{kind, payload, per_m}]` populated during
  Run, addressed by the reachability queries (`executor.reachable_nodes` `:339`,
  `loop._forward_reachable`/`_backward_reachable` `:113/126`).
- **Channel model (Phase 2)** couples R3/R8/R9 — input node must know its
  channel names (from its bound record) to render per-channel ports; executor
  channel resolution (`channel_sets`/`channel_recipes` `executor.py:157-236`)
  re-keys off the input node's per-channel ports.
- **Auto-layout (Phase 3)** must reserve the LEFT/RIGHT channel lanes (R8/R9)
  and a loop gutter lane (R10), exclude loop back-edges from ranking (mirror
  `topological_order`), and keep label-group members contiguous (R7).
