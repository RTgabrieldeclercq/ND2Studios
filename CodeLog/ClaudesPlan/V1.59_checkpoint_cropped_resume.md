# V1.59 — Cropped resume from a Checkpoint

## Goal

A **Checkpoint** node freezes the expensive upstream work (segmentation /
tracking) so downstream edits re-run instantly (V1.53). This change makes a
**cropped resume** work: set a **Preview Crop**, choose *Run cropped region*, and
the downstream pipeline runs on the crop **while still resuming from the
checkpoint** — the frozen full-frame masks are sliced to the crop rather than the
upstream being re-segmented from Input.

## The bug (from a real repro: Input → Registration[crop to common] → Checkpoint → DVC)

Three separate causes, found by tracing the attached `GELS_TFM_3D` pipeline where
"Run cropped region" from the checkpoint "went back to the Registration node,
completely neglecting the checkpoint":

1. **The registration crop was folded into the validity hash and is cleared at
   run start.** `_checkpoint_upstream_hash` hashed `self._crop_rect()` (preview ∩
   registration crop). `_on_run` clears `record._registration_crop` at the *start*
   of every Run — before `_checkpoint_resume_target` recomputes the hash — so a
   checkpoint frozen downstream of a "crop to common region" Registration node
   always mismatched on resume and fell through to a **full re-run from Input**.

2. **The checkpoint never froze the registration state.** In this pipeline the
   expensive upstream *is* the Registration node, but its output (per-M transforms
   + common crop) lives on the **record** (`_registration_by_m`,
   `_registration_crop`), not in the checkpoint's accumulators — and the record's
   registration state is cleared at run start. So even if the hash matched, a
   resume that skips the (frozen) Registration node would leave downstream with no
   drift correction.

3. **DVC ignored registration and crop entirely.** `_DVCJob._read_volume` read
   `record._raw_volume.get_volume(...)` directly — no drift correction, no crop —
   so DVC always correlated the raw, full-frame, drifting volumes regardless of
   the Registration node or the preview crop.

Cropping the frozen full-frame data is also semantically what the user wants — the
*already-computed* upstream shown/measured in the sub-region — which differs from
a fresh cropped Run that recomputes only the crop.

## Approach (`pages/pipelines_page.py`)

1. **Drop crop from the validity hash entirely.** `_checkpoint_upstream_hash` no
   longer hashes any crop. The preview crop is a downstream scoping concern; the
   registration crop is redundant (fully determined by the Registration node's
   params + channel wiring + source-file signature, all still hashed) *and* was
   harmful because it is cleared at run start. Result: a checkpoint after a
   "crop to common" Registration node stays valid on resume.

1b. **Freeze + restore the registration state.** `_run_checkpoint` snapshots
   `record._registration_by_m` / `_registration_interp_order` /
   `_registration_crop` and the `_reg_by_m` viewer bundle (arrays by reference,
   session RAM). `_restore_checkpoint` → new `_restore_registration_state`
   re-publishes them onto the record *before* the crop is computed, so the frozen
   (non-re-running) Registration node's drift correction + common crop reach every
   downstream reader. No-op for a plain analysis checkpoint.

1c. **DVC honors registration + crop.** `_DVCJob` gains `rect` / `transforms_by_m`
   / `interp_order`; `_read_volume` applies the frame-`t` 2D transform to every
   Z-slice (full frame) then crops to `rect` (register → crop), and `_run_dvc`
   passes `_crop_rect()` + `record._registration_by_m`. DVC now correlates the
   registered, cropped region like the rest of the pipeline.

2. **Re-scope the frozen data to the crop on restore.** New helpers:
   - `_effective_run_crop()` — the crop the Run will actually use (preview crop
     only when `_run_cropped`, intersected with the registration crop). Stable
     before `_run_active` flips, so checkpoint selection sees the right region.
   - `_crop_contains(outer, inner)` — containment test (a full-frame freeze,
     `outer=None`, contains any crop).
   - `_crop_analysis_result(res, rect, origin)` — a copy of a frozen
     `AnalysisResult` with its label masks (and secondaries) sliced to `rect`,
     **origin-aware** so masks frozen in registration-crop space slice correctly
     (`x0 = x - origin_x`). Voxel counts dropped (wrong for clipped objects).
   - `_recrop_restored_checkpoint(target, stored)` — slices every frozen result's
     masks and **re-derives** the measurement rows from the sliced masks +
     cropped channels via `_ensure_run_rows` (crop-aware `_materialize_channels_for_m`
     + `compute_measurements`), so every spatial column is correct in crop space —
     the same measurement path a fresh cropped Run uses. Tracks re-derived via
     `_set_track_overlay_state`.
   - `_restore_checkpoint` calls `_recrop_restored_checkpoint` when the effective
     Run crop differs from the freeze geometry (`snap["results_crop"]`).

3. **Guard checkpoint selection — mask-gated.** The containment check only
   protects **mask slicing**, so `_checkpoint_resume_target` applies it *only when
   the checkpoint actually froze masks* (`results_by_m` has label masks). A
   registration-only checkpoint (no masks — the repro pipeline) has nothing to
   slice out of bounds and is always resumable; the crop is applied to the live
   channel/volume reads, always valid. Without this exemption a preview crop drawn
   on a registration-cropped display could spuriously fail containment and send the
   Run back to re-register — the reported bug.

4. Resume + DVC status messages note the crop / "registered".

## Key decisions / notes
- **Re-derive rows** from the sliced masks rather than offsetting the frozen rows:
  the row schema has many spatial columns (px / µm / stage-µm centroids, bbox,
  deltas, neighbor distances) and re-deriving guarantees all are correct in crop
  space — identical to a fresh cropped Run. Cost: tracking is re-derived with the
  default per-M linker (an upstream Track Objects node's method isn't replayed in
  crop space); acceptable for a troubleshooting crop, and the expensive
  segmentation is still skipped.
- Slicing the frozen full-frame masks preserves the exact segmentation the full
  Run produced (objects clipped at the crop edge), which is the intended
  "cropped version of the already-computed pipeline".
- A checkpoint frozen at a crop only serves the same-or-contained crop; otherwise
  it invalidates and re-runs — correctness over cache aggressiveness (matches the
  V1.53 hashing philosophy).

## Follow-ups
- **Disk persistence of registration state.** `checkpoint_io.save_checkpoints`
  whitelists keys, so the new `reg_by_m` / `reg_interp_order` / `reg_crop` /
  `reg_bundle` are session-RAM only (not written to the `.checkpoints/` cache). A
  disk-reloaded checkpoint with `persist_to_disk` on therefore won't restore
  registration (graceful no-op — `_restore_registration_state` early-returns).
  Serialize the transforms (shifts/warps NPZ + crop) to make it survive restarts.
- **Preview-crop coordinate space on a registration-cropped display.** When the
  viewer shows a registration-cropped image, a rubber-band preview crop is captured
  in that display's coordinate space; `_crop_rect` intersects it with the
  registration crop in original-frame coords. Resolving this composition is part of
  the in-progress V1.60 registration-crop work; the checkpoint changes here compose
  through `_crop_rect` / `_effective_run_crop` so they inherit whatever V1.60
  settles on.
