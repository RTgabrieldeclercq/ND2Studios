# V1.65 — PyVista 3D Viewer (volumetric visualization + result overlays)

**Status:** Proposed (deep-dive / design document — no code yet)
**Author:** Claude (with G. Declercq)
**Scope:** Cross-cutting. A single reusable 3-D viewer widget, wired into (a) every
Import-tab file panel and (b) the Pipelines-tab viewer as a **2D ⇄ 3D toggle**, plus a
**"View in 3D"** path for result overlays — starting with **DVC** displacement/strain
fields and **PTV / SerialTrack** particle tracks.
**Dependency posture:** `pyvista` + `pyvistaqt` (+ their `vtk` transitive) are an
**optional, lazily-imported, `find_spec`-gated** extra — exactly the pattern the Cellpose
and StarDist nodes already use. The app must run byte-identically when they are absent; the
3-D affordances simply show a friendly "install to enable" placeholder.
**Research note:** PyVista/VTK are libraries, not a published scientific method, so no
`Research/` literature review is mandated by `CLAUDE.md`. The volume-rendering and glyph
techniques are standard VTK; references are collected in §15.

---

## 1. Goal

Give the McGhee Lab a true **3-D view of the data it already loads**, and of the
**measurement fields it already computes**, without disturbing the 2-D pipeline that the
recipe/analysis/export stack depends on.

Concretely, V1.65 must deliver:

1. A reusable `PyVista3DViewer` widget that renders the raw `(Z, H, W)` image volume for the
   current `(channel, M, T)` with **four selectable render modes** — volume rendering, maximum
   intensity projection (MIP), orthogonal slice planes, and isosurface — and **full M / T / Z
   navigation with time playback**, honoring **anisotropic voxel spacing** (`z_step_um` vs
   `pixel_size_um`), which for confocal stacks is the difference between a correct rendering and
   a squashed one.
2. A **2D ⇄ 3D toggle** in every Import-tab panel and in the Pipelines viewer, swapping the
   existing `MultiAxisViewer` for the 3-D viewer *in place* while preserving `(M, T, Z)` position
   and per-channel color/LUT state.
3. A **"View in 3D"** action on result overlays that opens the viewer (embedded or popped out)
   with the overlay drawn in 3-D:
   - **DVC**: the displacement field as glyph arrows and/or a warped structured grid, colored by
     any derived scalar (magnitude, a strain component, effective strain, divergence, …); optional
     Q-factor thresholding.
   - **PTV / SerialTrack**: per-track polylines/tubes, colored by time or velocity, with the raw
     image volume as optional context.
4. Keep everything **gated and non-fatal**: no hard dependency, no import-time VTK, no crash when
   the extras are missing, and no change to any existing 2-D behaviour.

**Non-goals for V1.65.** A standalone "3D View" nav page (the toggle + pop-out covers the ask more
cleanly and reuses existing viewer plumbing); GPU/OpenGL as a hard requirement (VTK software
rendering is an acceptable fallback); editing/annotation in 3-D (view-only); persisting 3-D scenes
to the `.nd2s` session; and volumetric export (a screenshot/animation export is a stretch goal, §12).

## 2. Background — where 3-D data lives today, and where it doesn't

### 2.1 The 2-D viewing stack

Both viewers we integrate with are instances of **`MultiAxisViewer`**
(`nd2studios/widgets/multi_axis_viewer.py:124`). It owns M/T/Z sliders, a channel "chip" strip, a
collapsible LUT sidebar, and an image canvas (`self.canvas`) that is either a pyqtgraph-backed
`GpuImageCanvas` or a legacy `ImageCanvas` (chosen at `multi_axis_viewer.py:261`). Its compositing
model — documented in the module header — is **per-channel `apply_lut` → multiply by per-channel
RGB → additive sum → clip to uint8**. The 3-D viewer will reuse the *same* LUT and color primitives
so the two views agree pixel-for-voxel:

- `apply_lut(frame, lo, hi, gamma)` — `nd2studios/widgets/lut_histogram.py:321`.
- `CHANNEL_COLORS` (name → RGB tuple) — `nd2studios/widgets/image_viewer.py:24`.

The public `MultiAxisViewer` API the 3-D viewer will **mirror** (so it can be a drop-in alternate):
`set_volume(...)` (`:707`), `set_channels(...)` (`:811`), `set_frame_timestamps(...)` (`:701`),
`coords() -> (m, t, z)` (`:1917`), `set_current_frame(...)` (`:466`), `channel_state()` (`:1904`),
`apply_channel_state(...)` (`:1937`), `refresh()` (`:450`), and the signals
`coords_changed(int,int,int)` and `channels_changed()`.

### 2.2 The volume data model — `MaterializedDataset`

Since V1.41 the record's volume is an in-RAM **`MaterializedDataset`**
(`nd2studios/backend/materialized_dataset.py:48`), not a lazy file handle. Each channel is stored as
`(M, T, Z, H, W)`, and the class deliberately preserves the old `LazyND2Volume` surface. The methods
that matter for 3-D are:

| Member | Signature / shape | Meaning |
|---|---|---|
| `get_volume(c, m, t, z_start=None, z_end=None)` | returns `(Z, H, W)` | **The true 3-D read path.** Preserves Z (unlike `get_frame`, which projects). This is what DVC already uses and what the 3-D viewer will call. (`:133`) |
| `channels[name]` | `(M, T, Z, H, W)` ndarray | Full in-RAM block, per channel. |
| `channel_names` | `List[str]` | Ordered channel names. |
| `n_multipoints / n_timepoints / n_zslices / height / width` | `int` | Axis extents. |
| `pixel_size_um` | `float` | Lateral (X = Y) sample spacing, µm. |
| `z_step_um` | `float` | **Axial** spacing, µm — the anisotropy source. |
| `dtype` | `np.dtype` | Per-pixel dtype (often `uint16`). |
| `shape` | `(M, T, Z, H, W)` | Convenience. |

The 3-D viewer will treat its volume argument **structurally** (duck-typed): anything exposing
`get_volume`, the `n_*` extents, `channel_names`, `pixel_size_um`, and `z_step_um`. That keeps it
working with `MaterializedDataset`, the still-present `LazyND2Volume`/`LazyMultiFileND2Volume`
(`nd2studios/backend/nd2_volume.py`), and any future volume backend.

### 2.3 Z is collapsed on the recipe/export path — so 3-D lives **only** in `_raw_volume`

This is the single most important architectural fact for the feature. Per `CLAUDE.md` and confirmed
in code: **Z is collapsed at load** for the recipe/analysis/export stream. Processed channels
(`record._processed_channels`, `record.processed_view()`) are `(T, H, W)` — the Z axis is *gone*.
The only place a full `(Z, H, W)` stack survives is the raw volume, reachable identically from both
integration points as **`record._raw_volume`** (a `MaterializedDataset`).

Consequences that shape the design:

- The image-volume render **must** read from `_raw_volume.get_volume(...)`, never from processed
  channels. When `n_zslices == 1` (a genuinely 2-D acquisition), the 3-D viewer degrades to a single
  textured plane and should say so rather than pretend depth exists.
- The recipe is not applied to the 3-D image by default (the recipe operates on the Z-collapsed
  stream). V1.65 renders the **raw** volume. Rendering a *deconvolved/restored* `(T,Z,H,W)` stack
  (see the V1.63 deconvolution plan, which keeps a full restored volume) is a natural follow-up but
  is out of scope here.

### 2.4 DVC results are already fully 3-D-aware

A DVC run yields a **`DVCResult`** dataclass (`nd2studios/core/dvc_registry.py:43`). Field shapes,
with `d ∈ {2,3}` and `grid = (Gy,Gx)` or `(Gz,Gy,Gx)`:

| Field | Shape | Units | Notes |
|---|---|---|---|
| `grid_coords` | `(*grid, d)` | voxels | Regular grid of subset centers over (Z,Y,X). |
| `displacement_field` | `(*grid, d)` | voxels | Component 0 = z (3-D); same axis order as coords. |
| `strain_field` | `(*grid, d, d)` | — | **Full rank-2 tensor** (trust the code shape, not the loose docstring). |
| `qfactor` | `(*grid,)` | ZNCC 0–1 | Correlation confidence — a natural opacity/threshold field. |
| `voxel_size_um` | `(z, y, x)` | µm | **Anisotropic**; from `pipelines_page.py:6035`. |
| `displacement_um()` / `magnitude` | `(*grid, d)` / `(*grid,)` | µm / vox | Convenience accessors (`:78`). |

Axis convention (mesh.py docstring): slowest-first, `(z, y, x)` in 3-D, `F[i,j] = ∂u_i/∂x_j`. The
grid is a **regular structured grid of subset centers** — a direct match for a PyVista
`StructuredGrid` (or `ImageData`) that we then `glyph` (arrows) and/or `warp_by_vector`.

**Runtime storage (important):** DVC results are **in-memory on the `PipelinesPage` widget only** —
`self._dvc_series_by_m[m][t]` (plus `_dvc_incr_by_m`, `_dvc_bg_by_mt`), declared at
`pipelines_page.py:1186`. They are **not** on the record, **not** in `analysis_results`, and **not**
persisted. A "View in 3D" button therefore reads the live series for the current M straight off the
page. A reusable coloring adapter already exists: `field_bundle_from_result(result)`
(`dvc_panel.py:90`) → a `FieldBundle`, then `serialtrack_analysis.scalar_field(fb, key)`
(`serialtrack_analysis.py:416`), which is already correct in 3-D (its `curl` returns a 3-vector,
stress handles 3-D). We reuse this rather than re-deriving strain.

### 2.5 PTV / SerialTrack tracks — Z-capable model, 2-D sources today

The runtime track structure to consume is **`TrackData`** (`serialtrack_analysis.py:74`), built on
demand by `build_track_data(rows, m, pixel_size_um, z_step_um, time_step)` (`:130`):

| Field | Shape | Meaning |
|---|---|---|
| `trajectories` | `(N_tracks, n_frames, D)` | NaN-gapped; one row per track. |
| `traj_ids` | `(N_tracks,)` | Track id per row. |
| `coords` | `{frame: (N, D)}` | Per-frame positions. |
| `ndim` | `2` or `3` | `D`. |
| `pixel_size_um`, `z_step_um`, `time_step` | scalars | Scaling / velocity basis. |

Coordinate order is `(y, x[, z])` — index 0 = y, 1 = x, 2 = z, in pixels. **Caveat, verified:** the
`D == 3` path is dormant — no current producer emits `centroid_z_px` (the measurement builder
`results_engine.compute_measurements` outputs only `centroid_y_px` / `centroid_x_px`), so **today
every track is `D == 2`.** Design implication: for present data, the natural "third dimension" is
**time** — render `(x, y, t)` space-time tubes, with time or velocity as the color. When a 3-D
centroid source arrives (imported volumetric rows), the identical code renders true `(x, y, z)`
tubes because `TrackData` already carries `z_step_um` and the projection indices are axis-agnostic.

The exact 2-D thing to generalize is `SerialTrackPanel._render_trajectories`
(`serialtrack_panel.py:418`): it already builds per-track NaN-gapped polylines, uses projection axis
pairs `{"XY":(1,0), "XZ":(1,2), "YZ":(0,2)}` (confirming 0=y,1=x,2=z), colors by Time or
Displacement, and caps at 800 tracks. Track colors can reuse
`track_overlays.generate_track_colormap(track_ids)` (`track_overlays.py:24`). Tracks are read on the
page via `_overlay_rows()` (`pipelines_page.py:3418`); the panel feed is `_populate_serialtrack_panel(m)`
(`:3559`). On the Results page the canonical store is `self._measurements`.

## 3. Library choice — why PyVista + pyvistaqt

### 3.1 Options considered

| Option | Volume rendering | Qt embedding | Glyphs/tubes/isosurface | Verdict |
|---|---|---|---|---|
| **Raw VTK** | Yes (gold standard) | `QVTKRenderWindowInteractor` | Yes, verbose | Maximum control, high boilerplate; we'd re-implement PyVista. |
| **pyqtgraph `GLViewWidget`** | `GLVolumeItem` (basic) | Native (already a dep) | Limited; manual meshes | Cheap, but weak volume TF control, no true MIP/iso convenience, awkward glyphs. |
| **vedo** | Yes (VTK wrapper) | Possible | Yes | Capable, smaller ecosystem/docs than PyVista. |
| **napari** | Excellent for imaging | It *is* an app | Points/vectors/tracks layers | Heavyweight; brings its own app/event loop — awkward to embed as a panel inside our Qt app. |
| **PyVista + pyvistaqt** | Yes (`add_volume`, TF, blending) | **`pyvistaqt.QtInteractor`** embeds cleanly in a `QWidget` | `glyph`, `warp_by_vector`, `tube`, `contour`, slice planes — all one-liners | **Chosen.** |

### 3.2 Decision & rationale

**PyVista** gives us all four render modes and both overlay types through a concise, well-documented
API on top of VTK's mature volume mapper; **pyvistaqt** provides `QtInteractor`, a `QWidget` that
drops straight into our layouts and rides our existing pop-out mechanism. Both speak `qtpy`, so they
bind to **PySide6** (our required toolkit — `CLAUDE.md`) when `QT_API=pyside6` is set. The mapping
from feature to API is direct: `add_volume(...)` (volume + MIP via `mapper='fixed_point'` /
`blending='maximum'`), `add_mesh(grid.contour(...))` (isosurface), `add_mesh_slice_orthogonal()` or
three `add_mesh(vol.slice(...))` planes (ortho slices), `glyph(orient=, scale=)` (DVC arrows),
`warp_by_vector()` (DVC warp), `lines_from_points(...).tube(...)` (PTV tubes).

### 3.3 Dependency strategy

Following the Cellpose/StarDist precedent (`importlib.util.find_spec(...)` →
`STARDIST_AVAILABLE`, lazy import, friendly `ImportError` — `stardist_segmentation.py:31`):

```python
import importlib.util
PYVISTA_AVAILABLE: bool = (
    importlib.util.find_spec("pyvista") is not None
    and importlib.util.find_spec("pyvistaqt") is not None
)
```

- **No top-level `import pyvista`** anywhere that loads at app start. VTK import is slow and pulls
  OpenGL; it is imported lazily *inside* the viewer widget's constructor, guarded by the flag.
- When unavailable: the toggle button is present but shows a **placeholder panel** ("3-D view needs
  `pip install pyvista pyvistaqt` — 2-D view still available") instead of a live canvas. Nothing
  crashes; 2-D is untouched.
- **`requirements.txt`:** per the `CLAUDE.md` rule that gated optional extras are *not* pinned in
  `requirements.txt` (as with cellpose/stardist), the hard requirements file stays lean. We add a
  clearly-marked **comment** documenting the optional install and known-good version constraints
  (§13), so users can enable it in one line. `qtpy` (pulled in by pyvistaqt) must resolve to PySide6.

## 4. Architecture of the 3-D subsystem

### 4.1 Layering

The design obeys the `CLAUDE.md` boundary rule — **backend is Qt-free and, here, also
PyVista/VTK-free**. The heavy graphics dependency is confined to the widget layer.

```
                    ┌───────────────────────────────────────────────┐
   record._raw_volume (MaterializedDataset)  DVCResult   TrackData    │
                    │           │                │            │       │
        ┌───────────▼───────────▼────────────────▼────────────▼──────┐
 BACKEND│ backend/viz3d/            (PURE numpy — no Qt, no pyvista)   │
 (pure) │  • prep.py   volume→(Z,H,W) uint8 + spacing + LUT           │
        │  • overlays.py  DVCResult→points/vectors/scalars;           │
        │                 TrackData→polyline segments; labels→volume  │
        └───────────▲───────────────────────────────────────────────┘
                    │ plain numpy arrays + small dataclasses
        ┌───────────┴───────────────────────────────────────────────┐
 WIDGET │ widgets/viewer3d/         (Qt + pyvista, gated)             │
        │  • pyvista_viewer.PyVista3DViewer(QWidget)  ← QtInteractor  │
        │  • controls (mode switch, channel chips, M/T/Z, opacity)    │
        │  • viewer3d_dialog.Viewer3DDialog  (pop-out)                │
        │  • placeholder.Missing3DDeps (when not PYVISTA_AVAILABLE)   │
        └───────────▲───────────────────────────────────────────────┘
                    │ builds numpy off-thread
        ┌───────────┴───────────────────────────────────────────────┐
 WORKER │ workers/volume3d_worker.VolumeBuildWorker(BaseWorker)       │
        │  reads get_volume(...) for enabled channels, applies LUT,   │
        │  returns {name:(Z,H,W) uint8} + spacing  (NO pyvista here)  │
        └────────────────────────────────────────────────────────────┘
```

**Threading contract (non-negotiable):** VTK/OpenGL objects may only be touched on the **GUI
thread**. Therefore the worker produces *only* numpy arrays; every `pyvista` actor/mapper is created
and mutated on the main thread inside `PyVista3DViewer`, in the worker's `finished` slot.

### 4.2 New modules & responsibilities

**Backend (pure numpy, unit-tested headlessly):**

- `nd2studios/backend/viz3d/__init__.py`
- `nd2studios/backend/viz3d/prep.py`
  - `channel_volume(volume_src, c, m, t, z_start, z_end) -> (np.ndarray (Z,H,W), Spacing)` — thin,
    safe wrapper over `get_volume` with clamping and single-Z handling.
  - `to_uint8(vol, lo, hi, gamma) -> (Z,H,W) uint8` — Z-stack generalization of `apply_lut` (apply
    per-plane or vectorized; must match the 2-D LUT numerically).
  - `Spacing` dataclass: `(dz, dy, dx)` in µm, from `z_step_um`/`pixel_size_um`, with a normalized
    form so the smallest axis = 1.0 for stable camera framing.
  - `color_rgb(name_or_hex) -> (r,g,b) float in [0,1]` reusing `CHANNEL_COLORS`.
- `nd2studios/backend/viz3d/overlays.py`
  - `dvc_field(result) -> DVCField` — points `(N,3)` in **µm** (grid_coords × voxel_size_um, padded
    to 3-D for the 2-D case), vectors `(N,3)` (displacement_um, padded), and a dict of named scalar
    arrays `(N,)` (magnitude, e_xx…, eff_strain, div, curl-mag, detF, von_mises, qfactor) obtained
    via the existing `field_bundle_from_result` + `scalar_field`. Also returns `grid_shape` so the
    widget can build a `StructuredGrid` for `warp_by_vector`.
  - `ptv_polylines(track_data, up_to_frame=None, third_axis='time'|'z') -> PtvTracks` — list of
    `(P_i, 3)` point arrays (one per track, NaN-split into finite segments), matching track ids, and
    a suggested scalar per vertex (cumulative time or per-segment velocity). `(x, y, z_or_time)` in
    world units; caps at a configurable max track count (default 800, mirroring the 2-D panel).
  - `label_volume(masks) -> (Z,H,W) int` — optional segmentation-overlay helper for later.

**Widget (Qt + pyvista, gated):**

- `nd2studios/widgets/viewer3d/__init__.py` — exports `PyVista3DViewer`, `Viewer3DDialog`,
  `PYVISTA_AVAILABLE`.
- `nd2studios/widgets/viewer3d/pyvista_viewer.py` — the main widget (§4.3).
- `nd2studios/widgets/viewer3d/controls.py` — the control bar (mode switcher, channel chips,
  M/T/Z sliders + play, opacity/threshold, reset-camera, screenshot). Built with the
  `icon_button` / `scaled()` / Dracula-object-name conventions (the `nd2studios-widget-layout`
  skill).
- `nd2studios/widgets/viewer3d/placeholder.py` — `Missing3DDeps(QWidget)`.

**Worker:**

- `nd2studios/workers/volume3d_worker.py` — `VolumeBuildWorker(BaseWorker)` (base at
  `workers/base_worker.py:10`): `run_task()` reads the enabled channels' `(Z,H,W)` blocks, applies
  LUT → uint8, emits `progress`, returns `{name: (Z,H,W) uint8}` + `Spacing` + the `(m,t)` it was
  built for (so a stale result can be dropped).

### 4.3 The reusable `PyVista3DViewer` widget

A `QWidget` whose center is a `pyvistaqt.QtInteractor` (lazy-constructed) and whose controls mirror
enough of `MultiAxisViewer` to be a drop-in alternate. Proposed public surface (full sketch in
Appendix A):

```python
class PyVista3DViewer(QWidget):
    coords_changed = Signal(int, int, int)   # (m, t, z)  — kept in lockstep with the 2-D viewer
    channels_changed = Signal()

    def set_volume(self, volume, *, channel_display=None, z_mode="max",
                   z_index=0, m=0, t=0, z=0, stage_xy_um=None): ...   # matches MultiAxisViewer:707
    def set_channels(self, channels, *, channel_display=None, n_multipoints=1, m=0): ...
    def set_frame_timestamps(self, timestamps): ...
    def coords(self) -> tuple[int, int, int]: ...
    def set_current_frame(self, m=None, t=None): ...
    def channel_state(self) -> dict: ...
    def apply_channel_state(self, state: dict): ...
    def refresh(self): ...
    def reset_camera(self): ...                 # analog of canvas.reset_zoom()

    # 3-D specific
    def set_render_mode(self, mode: str): ...    # "volume" | "mip" | "slices" | "isosurface"
    def set_overlay(self, overlay): ...          # DVCField | PtvTracks | None
    def screenshot(self, path: str): ...
```

Matching `set_volume`'s signature means the **existing call sites feed the 3-D viewer unchanged**
(FilePanel `file_panel.py:500`, Pipelines `_show_preview_volume`). `channel_state()` /
`apply_channel_state()` let the toggle hand color/LUT state back and forth with the 2-D viewer so
the two never diverge.

### 4.4 Off-thread volume build

Reading and LUT-ing a `(Z,H,W)` block for several channels is fast from RAM but not free (a 60×2048×2048
`uint16` stack is ~500 MB → ~250 MB uint8). To keep the GUI responsive during first render, M/T
changes, and playback stepping, the widget:

1. On any `(m, t)` / channel-enable / LUT change, cancels the in-flight `VolumeBuildWorker` and
   starts a fresh one for the enabled channels.
2. In the `finished(result)` slot (main thread), (re)builds/updates the pyvista actors with the new
   uint8 volumes and current spacing, then `render()`s.
3. Coalesces rapid slider moves with a short debounce timer (the `MultiAxisViewer` already debounces
   LUT/color changes; we mirror that).

A small **LRU cache** of built uint8 volumes keyed by `(name, m, t, lut-signature, z-range)` makes
scrubbing and time playback smooth without unbounded memory (bounded by count and total bytes; wired
to the existing `MemoryMonitor` pressure signals so it flushes under load).

### 4.5 Pop-out dialog

`Viewer3DDialog(QDialog)` hosts a `PyVista3DViewer` for the "View in 3D" result path. In the
Pipelines tab, because the viewer lives inside `self._viewer_container`, the **existing**
`_toggle_popout("viewer")` mechanism (`pipelines_page.py:1251`, which reparents the live container
into a `PopOutWindow`) already gives the 3-D view a maximize/pop-out for free once the toggle wraps
the viewer — so the standalone dialog is mainly for the DVC/PTV result buttons that want a separate
window without touching the page layout.

### 4.6 Gating & graceful placeholder

`PyVista3DViewer.__init__` checks `PYVISTA_AVAILABLE`. If false, it lays out `Missing3DDeps` (an
install hint + a "Copy pip command" button) instead of a `QtInteractor`, and all `set_*` methods
become no-ops. The toggle remains usable (it just shows the placeholder), so discovery works even
before the extra is installed.

## 5. Rendering modes (mapped to VTK/PyVista APIs)

All modes operate on a `pyvista.ImageData` (a.k.a. uniform grid) built per channel from the uint8
`(Z,H,W)` block, with `spacing=(dz, dy, dx)` set from §5.5. Multi-channel scenes add one actor per
enabled channel.

### 5.1 Volume rendering (default)

`plotter.add_volume(grid, cmap=<channel color ramp>, opacity=<transfer function>, blending="composite")`
per channel. The **opacity transfer function** maps intensity→alpha; we expose a small set of presets
(linear, "sigmoid"/`opacity="sigmoid"`, and a low-end-suppressing ramp good for fluorescence) plus a
master opacity slider. Per-channel color comes from `CHANNEL_COLORS`, rendered as a black→color ramp
so additive overlap reads like the 2-D composite. For multi-channel, **additive** blending
(`blending="additive"`) most closely matches the 2-D "additive sum" model; composite is offered as an
alternative for depth cueing.

### 5.2 Maximum intensity projection (MIP)

Same volume actor with `blending="maximum"` (VTK's MIP ray function). This is the 3-D analog of a max
Z-projection and is the fastest, crispest mode for sparse/bright structures — a good default when the
volume is large or the GPU is weak.

### 5.3 Orthogonal slice planes

`grid.slice_orthogonal(x=, y=, z=)` → three planes, added with the channel color LUT; positions driven
by three sliders (defaulting to the volume center, and to the current 2-D `z` for the Z-plane so the
toggle lands on "the slice you were looking at"). Optionally `add_mesh_slice_orthogonal(...)` to expose
VTK's interactive plane widgets for click-drag repositioning.

### 5.4 Isosurface

`grid.contour(isosurfaces=[level], scalars=...)` (marching cubes) → a `PolyData` surface, added with
per-channel color and adjustable opacity. A threshold slider sets `level` (seeded from an Otsu or a
percentile of the intensity histogram so the first surface is sensible). Best for high-contrast,
well-separated objects; noisy data will produce many shells, which the threshold slider tames.

### 5.5 Anisotropic voxel spacing & world transform

Confocal Z-step is routinely several × the XY pixel; rendering on a unit grid squashes the volume.
We set `ImageData.spacing = (dz, dy, dx)` with `dz = z_step_um`, `dy = dx = pixel_size_um`. To keep the
camera well-framed regardless of absolute scale, `prep.Spacing` also exposes a **normalized** form
(divide by the min axis). Physical µm is retained for axis bounds/scale annotations. VTK's array axis
order is `(Z, Y, X)` for an `ImageData` filled from a `(Z,H,W)` block, so spacing is applied in that
order — consistent with the DVC/PTV `(z,y,x)` convention (§2.4–2.5), which avoids a whole class of
transpose bugs.

### 5.6 Multi-channel compositing & LUT reuse

The uint8 volumes come from the same `apply_lut(lo, hi, gamma)` the 2-D viewer uses, read from
`record.channel_display[name]` (`{enabled, color, lut_lo, lut_hi, lut_gamma}`). Enabled channels only
are built (saving memory/time). Changing a chip color or LUT slider re-runs the build for that channel
and updates its actor — the `channels_changed` signal fires so a paired 2-D viewer can stay in sync.

## 6. Axis navigation & playback (M / T / Z)

### 6.1 Controls

A compact control bar (mirroring `MultiAxisViewer`'s slider row, built per the widget-layout skill):
an **M** selector (visible when `n_multipoints > 1`), a **T** slider with a **play** button (visible
when `n_timepoints > 1`), a **Z-range** double-slider `[z_start, z_end)` for clipping the rendered
sub-stack, a **render-mode** switcher (segmented `QToolButton`s or a combo), a **master opacity /
isolevel** slider (context-sensitive to the mode), **reset camera**, and **screenshot**. Channel
chips reuse the existing `ChannelChip` look so the two viewers feel identical.

### 6.2 Time playback strategy

Volume rendering a new timepoint means rebuilding the uint8 volume(s) for that `t` and swapping the
actor's scalars — cost dominated by the read+LUT, which the worker + LRU cache absorb. Playback:

- A `QTimer` at the chosen FPS advances `t`; each tick pulls from cache or kicks a build.
- If builds can't keep up, we **drop frames** (skip to the latest requested `t`) rather than queue —
  playback stays real-time, just coarser, exactly how a video scrubber behaves.
- A "downsample for playback" toggle (e.g. XY/Z stride 2) trades resolution for frame rate on big
  stacks; full resolution returns when playback stops. This reuses the DVC node's existing
  `downsample` mental model.

### 6.3 Z-range clipping

`z_start/z_end` are passed straight to `get_volume(..., z_start, z_end)` so we never materialize
planes we won't show. Clipping is the cheapest way to focus on a sub-slab and speeds every mode.

## 7. Result overlays in 3-D

### 7.1 DVC displacement / strain fields

From `DVCField` (§4.2): build a `pyvista.StructuredGrid` from `grid_coords × voxel_size_um` (µm,
padded to 3-D when `d==2` so 2-D DIC fields render on a plane in the 3-D scene). Attach every named
scalar and the displacement vectors as point data. Then offer, as toggles:

- **Glyphs:** `grid.glyph(orient="displacement", scale="magnitude"|fixed, factor=k)` → arrow field,
  colored by the selected scalar (magnitude, `e_xx…`, `eff_strain`, `div`, `curl`, `detF`,
  `von_mises`, `qfactor`). A magnitude/`qfactor` **threshold** hides low-confidence or near-zero
  arrows (declutter).
- **Warp:** `grid.warp_by_vector("displacement", factor=k)` → the deformed grid as a colored mesh
  (surface or wireframe), the clearest way to *see* the deformation; `factor` exaggerates small
  displacements.
- **Context:** optionally render the raw image volume (re-read via `record._raw_volume.get_volume`,
  since the stored DVC backdrop is only a 2-D MIP) at low opacity beneath the field.

Scalars come from the **existing** `field_bundle_from_result` → `scalar_field` path (already
3-D-correct), so DVC math is not duplicated. Colormaps use perceptually-uniform ramps (viridis/turbo)
with a shared color bar.

### 7.2 PTV / SerialTrack tracks

From `PtvTracks` (§4.2): each track → a `pyvista` polyline (`lines_from_points`) optionally thickened
with `.tube(radius=r)`; colored by **time** (cumulative fraction along the track) or **velocity**
(per-segment displacement / `time_step`), matching `_render_trajectories`' two color modes. Track
count is capped (default 800). Because current data is `D==2`, the default third axis is **time**
(space-time tubes); a "z / time" switch selects the axis, and true `(x,y,z)` tubes appear automatically
once `centroid_z_px` exists. Optional current-frame **points** (`coords[frame]`) mark live particle
positions; the raw volume can sit underneath as faint context.

### 7.3 Segmentation label volumes (bonus / later)

`label_volume(masks)` → an `ImageData` of integer labels rendered as isosurfaces or a categorical
volume; lets Cellpose/StarDist results show as 3-D blobs. Scaffolded in `overlays.py` but wired only
if time permits in V1.65.

### 7.4 Overlay adapters live in the backend

All three adapters are **pure numpy** in `backend/viz3d/overlays.py`, returning plain arrays +
small dataclasses. The widget converts those to pyvista objects on the main thread. This keeps overlay
geometry **unit-testable without a display** (§11) and keeps VTK out of the backend.

## 9. Data-shape contracts & edge cases

- **Single-Z acquisitions (`n_zslices == 1`).** No true depth. The viewer renders one textured plane
  and surfaces a subtle "2-D data — no Z" note; MIP/volume/iso collapse to the plane, ortho-slices
  degenerates to the single XY plane. The toggle still works (useful for overlays).
- **dtype.** Volumes are commonly `uint16`; LUT → uint8 happens in the backend `to_uint8`, matching
  2-D. Float volumes (e.g. mean projection, deconvolved) are handled by the same LUT path.
- **Anisotropy.** Always apply `(dz, dy, dx)`; never assume isotropy. `z_step_um`/`pixel_size_um`
  come from the volume, falling back to `1.0` (documented as "uncalibrated — geometry may be
  distorted").
- **Large stacks.** Guard first render with an estimated-bytes check against the `MemoryMonitor`
  bands (`Settings.MEMORY_PRESSURE_*`); above a threshold, auto-suggest MIP + playback downsample and
  prompt before building. Never duplicate `_raw_volume`.
- **2-D DIC vs 3-D DVC.** `DVCResult` may be `d==2`; `dvc_field` pads to 3-D so a DIC field renders as
  a plane in the 3-D scene without special-casing the widget.
- **Empty / NaN.** DVC subsets can be NaN (failed correlation); glyphs skip NaN. PTV trajectories are
  NaN-gapped; polylines split into finite runs. Zero tracks / zero grid → a clear "no field/tracks"
  message, not an empty crash.
- **Coordinate order.** `(Z,Y,X)` everywhere — image blocks, `ImageData` spacing, DVC `(z,y,x)`, PTV
  `(y,x,z)` mapped explicitly. Documented in each adapter's docstring.

## 10. Performance & memory

- **Reads from RAM**, not disk (`MaterializedDataset`), so the cost is LUT + VTK upload. The worker
  keeps both off the paint path.
- **LRU render-block cache** keyed by `(name, m, t, lut-sig, z-range)`, bounded by entry count *and*
  total bytes; subscribed to `MemoryMonitor` so it drops under pressure (reusing the V1.41
  resource-aware machinery).
- **Playback** drops frames rather than queuing; optional stride downsample.
- **GPU vs software.** VTK uses the GPU when available and falls back to software rendering; we detect
  and, on software, default to MIP and warn that volume rendering may be slow. This mirrors the
  app's existing `USE_GPU_DISPLAY` opt-out philosophy (`Settings`), though it's a separate VTK path.
- **Lazy everything:** no VTK import, no `QtInteractor`, and no 3-D volume built until the user first
  toggles 3-D or clicks "View in 3D".

## 11. Testing & verification strategy

Because the sandbox has no display and the extras aren't installed, verification is layered:

1. **Backend unit tests (runnable now, no display):** `tests/viz3d/test_prep.py` and
   `test_overlays.py` — assert `to_uint8` matches `apply_lut` plane-by-plane; `channel_volume`
   clamps Z-range and handles single-Z; `Spacing` normalization; `dvc_field` produces correct point
   counts, µm scaling (grid_coords × voxel_size_um), 2-D→3-D padding, and scalar keys; `ptv_polylines`
   splits NaN gaps, caps track count, and maps `(y,x[,z])`→world `(x,y,z_or_t)` correctly. These are
   pure numpy — deterministic and fast.
2. **Import/compile gate:** `python -m py_compile` across all new/modified files; import
   `backend.viz3d.*` (pure numpy) in the sandbox to catch signature/logic errors.
3. **Gating test:** with pyvista absent, assert `PYVISTA_AVAILABLE is False`, that importing the
   widget module doesn't import VTK, and that `PyVista3DViewer` lays out the placeholder and its
   `set_*` are no-ops. (Runnable once PySide6 is present; guarded otherwise.)
4. **Headless widget-layout checks (per the `nd2studios-widget-layout` skill §6):** build just the
   control bar in a `QApplication`, `show()`, `processEvents()`, assert buttons carry non-null icons,
   spin/sliders meet min sizes, and the mode switcher toggles state. `QTimer.singleShot(200,
   app.quit)` — never block on `exec()`.
5. **Off-screen render smoke test (developer machine / CI with extras):** `pv.OFF_SCREEN = True`
   (`pv.start_xvfb()` on Linux), build a tiny synthetic `(8,16,16)` volume, run each of the four modes
   + a DVC glyph + a PTV tube, `screenshot()` to PNG, assert non-empty non-uniform output. This is the
   end-to-end proof that the VTK path works; documented in the plan as the maintainer's local check
   since it can't run in this sandbox.
6. **Manual QA checklist** (in the PR): toggle 2D⇄3D on Import and Pipelines preserves `(m,t,z)` +
   LUTs; playback stays responsive on a real stack; DVC/PTV "View in 3D" render with correct scaling.

A **verification subagent** will review the diff for backend-purity violations (no PySide6/pyvista
imports under `backend/`), missing `find_spec` guards, and any top-level VTK import.

## 13. Risks & mitigations

- **pyvistaqt ↔ PySide6 binding.** pyvistaqt uses `qtpy`; if `PyQt5` is also importable, qtpy may pick
  it. Mitigation: set `os.environ.setdefault("QT_API", "pyside6")` *before* importing pyvistaqt, and
  document it. Pin known-good ranges (indicatively `pyvista>=0.43`, `pyvistaqt>=0.11`, `vtk>=9.2`);
  finalize against the user's installed PySide6 at implementation time.
- **VTK/OpenGL on the target machine.** Some lab machines/remote sessions lack a usable GL context.
  Mitigation: detect and fall back to MIP + a warning; never hard-fail; keep 2-D fully functional.
- **Threading.** Touching VTK off the GUI thread crashes. Mitigation: worker returns numpy only; all
  actor ops on the main thread (enforced in review, §11).
- **Memory blow-up on huge stacks.** Mitigation: no `_raw_volume` duplication; LRU-bounded uint8
  blocks; `MemoryMonitor`-gated first render; playback downsample.
- **DVC results are ephemeral & page-local.** A run must exist in the current session. Mitigation:
  enable "View in 3D" only when `_dvc_series_by_m` is populated; clear messaging otherwise.
- **PTV is 2-D today.** Mitigation: default to space-time tubes; the z-axis path is present and
  tested with synthetic 3-D data so it's ready when `centroid_z_px` sources arrive.
- **`requirements.txt` policy.** Gated extras are, by `CLAUDE.md` precedent, not pinned there.
  Mitigation: a clearly-labeled comment block documents the optional install so it's discoverable
  without becoming a hard dependency (revisit with G. Declercq if he'd prefer it pinned).
- **Can't GUI-test in this environment.** Mitigation: the layered strategy (§11) puts all
  display-free logic under unit tests; the off-screen render smoke test is documented for the
  maintainer's machine.
