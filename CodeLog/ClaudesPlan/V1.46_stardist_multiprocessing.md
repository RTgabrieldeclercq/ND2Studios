# V1.46 — StarDist multiprocessing (many-core CPU throughput)

## Goal

Let StarDist segmentation process **multiple frames concurrently** on a
many-core CPU workstation, instead of the current strictly-sequential
one-frame-at-a-time loop. Speedup should scale with available cores and be
bounded by available RAM, so the lab workstation runs N frames at once while a
laptop stays well-behaved.

## Background — why it's sequential today

`StarDistSegmentationPipeline.run()` drives `run_planes_to_labels(..., n_workers=1)`
([stardist_segmentation.py](../../nd2studios/backend/analysis/stardist_segmentation.py)).
The `n_workers=1` is deliberate and correct for the **thread** pool:

- The StarDist model is a module-level singleton
  ([celltracker/segmentation.py](../../nd2studios/backend/celltracker/segmentation.py)).
- TensorFlow op-parallelism is pinned to a single inter/intra-op thread
  (`_ensure_tf_threading`) — removing that cap measured ~10× slower for
  StarDist's tiled inference.
- `predict_instances` on a shared TF graph is not thread-safe.

So raising `n_workers` on the *thread* pool cannot help — threads share one
model + the GIL and serialize. The plane runner already streams one frame at a
time, so **RAM is not the current limiter; CPU throughput is.**

## Approach — process parallelism (chosen after confirming CPU target)

Run StarDist across **separate processes** (`ProcessPoolExecutor`, spawn
context). Each worker process loads its **own** model + TF (each still pinned to
1 op-thread), so N processes × 1 thread ≈ N cores, with no shared-state hazard.

Key design decisions:

1. **Parent owns the lazy source and the label sink.** Frames are read one at a
   time in the parent (`read_plane`) and shipped to workers as plain ndarrays.
   The lazy ND2/disk reader is never opened in a child, and the parent remains
   the single writer of the streaming `LabelStackWriter` / in-RAM stack. Masks +
   measurement rows come back from workers.
2. **All per-frame CPU runs in the worker.** normalize → `predict_instances` →
   `filter_and_relabel` → `regionprops` all happen in the child, so the parent
   only reads/writes and never becomes the bottleneck.
3. **Bounded in-flight window (~2×workers frames).** We do not submit all T
   frames up front (that would read the whole stack into RAM and break the
   streaming bound). We prime ~2×workers frames, then submit the next frame each
   time one completes. Parent RAM ≈ window × (frame + mask).
4. **Spawn context, module-level worker fns.** Windows uses spawn; init state
   and the worker fn are module-level so they pickle. `run.py` already guards on
   `if __name__ == "__main__"`, so spawned children don't re-launch the GUI.
5. **RAM- and core-gated worker count.** New `recommended_process_count()` in
   `resources.py` = min(physical cores, available_RAM / ~2 GB per worker, cap 8).
   Each StarDist/TF process costs ~1.5–2 GB.
6. **GPU stays sequential.** When the runtime GPU flag is on, MP just makes
   processes fight over one card + VRAM. On GPU we keep the existing single-model
   path (true GPU batching is a separate future item, noted in the plan).
7. **Small jobs / 1 worker fall back to the existing sequential path.** Process
   startup (per-process TF init, a few seconds each) isn't worth it for a handful
   of frames, so `workers <= 1` or `T < 2` uses the current thread path
   unchanged — identical behavior, zero risk for the common small case.
8. **User override.** A new `n_processes` param (0 = auto) lets power users pin
   the count; auto is the RAM/core-gated default.

## Files to modify

- **new** `nd2studios/backend/analysis/mp_stardist.py` — backend-pure MP runner
  (`run_stardist_multiprocess`, `_init_worker`, `_segment_frame_worker`).
  Returns a `PlaneRunOutput` so the node's summary code is shared.
- `nd2studios/utils/resources.py` — add `recommended_process_count()`.
- `nd2studios/backend/analysis/stardist_segmentation.py` — add `n_processes`
  ParamSpec; compute effective worker count (GPU→1, else RAM/core-gated);
  branch to the MP runner when workers > 1, else keep the sequential path.
- `CodeLog/Updates/CHANGELOG.md`, `CodeLog/Architecture/ARCHITECTURE.md`.

## Non-goals

- GPU batched inference (single forward pass over a frame stack) — separate item.
- Multiprocessing for the Cellpose node — Cellpose has its own batching and GPU
  path; not touched here.

## Verification

- Small stack (T<2, GPU, or 1 worker) → identical output to sequential path.
- Multi-frame CPU run → same label masks/measurements as sequential (order
  independent), wall-clock scales with worker count.
- Cancel mid-run stops submitting and shuts the pool down cleanly.
- Streaming sink path (memory-constrained) still bounds parent RAM to the window.
