# V1.33 — Phase 1: Profiling & Measurement Baseline

## Goal

Establish a reproducible profiling harness for ND2Studios and capture a
**baseline** of where time and memory currently go. This is the input to
the 7-phase performance optimization plan (`00_README.md` ..
`07_phase_gpu_multires.md`). Without baseline numbers we cannot validate
that any subsequent optimization is an actual improvement.

This phase deliberately **does not** modify any production code. The only
additions to `nd2studios/` are a backend-pure helper module
(`nd2studios/utils/profiling.py`) that has no Qt dependencies and could
be reused by future optimization tests.

## Why now

The user has flagged several perceived performance issues — slow tab
switches, slow per-tab analysis, RAM underused. These are *hypotheses*;
profiling assumptions are wrong roughly half the time. We need an
empirical map of:

- cold file-open latency,
- per-frame fetch latency under M / T / Z scrubbing,
- tab transition latency,
- analysis-pipeline runtime,
- process RSS and Python-side allocations over a session.

## Approach

Bolt a self-contained `profiling/` directory next to the existing
`tests/` and `scripts/` directories. The harness drives ND2Studios's
*real* loader / volume / analysis code paths (no fakes, no mocks) and
emits a single JSON snapshot per run, suitable for git-tracked
before/after comparisons.

### How the harness maps onto the existing code

| Phase 1 doc placeholder            | Real ND2Studios target                                    |
| ---------------------------------- | --------------------------------------------------------- |
| `load_image_file(path)`            | `LazyND2Volume(path)` or `LazyMultiFileTIFFVolume([path])` |
| `handle.get_plane(t, m, z)`        | `volume.get_frame(c=0, m=m, t=t, z=z, z_mode="none")`     |
| `MainWindow` / `tab_widget`        | `nd2studios.core.main_window.MainWindow` + its `_stack`   |
| `detect_bright_spots`, etc.        | `AnalysisPipeline.get_pipelines()` (registry-driven)      |

For analysis we drive registered pipelines (`Bright / Dark Spots`,
`Histogram Threshold Segmenter`, `Tear Detection`, `Manual Mask`) on a
small synthetic `(T, H, W)` channel because real ND2 files may not be
present on every machine.

### File layout

```
profiling/
├── __init__.py
├── README.md                       # how to run + what each scenario measures
├── harness/
│   ├── __init__.py
│   ├── fixtures.py                 # PROFILING_TEST_DATA_DIR env var + TestFile records
│   ├── scenario_load.py            # cold open + first frame
│   ├── scenario_scrub.py           # walk T (and Z and M) at one frame at a time
│   ├── scenario_tab_switch.py      # offscreen Qt — walk through pages, time each
│   ├── scenario_analysis.py        # run each registered AnalysisPipeline on synth data
│   └── run_all.py                  # aggregator → baselines/<label>.json
├── baselines/                      # JSON snapshots (gitignored except .gitkeep)
└── reports/                        # py-spy flamegraphs (gitignored except .gitkeep)
```

Plus one backend module:

```
nd2studios/utils/
├── __init__.py
└── profiling.py                    # Measurement, measure(), fps_from_durations()
```

### Key decisions

1. **Backend-pure helpers, Qt-free** — `nd2studios/utils/profiling.py`
   only depends on `psutil`, `tracemalloc`, `gc`, `time`. It is safe to
   import from any context (Qt, headless, tests). Matches CLAUDE.md
   "backend purity" rule.
2. **Test data is opt-in** — fixtures look at `$PROFILING_TEST_DATA_DIR`
   (or `~/profiling_data/`). Scenarios skip cleanly when files are
   absent so the harness can still run on machines without lab data.
3. **Synthetic frame for analysis** — `scenario_analysis` does not
   require lab data; it generates a 32-frame `(T, 256, 256)` uint16
   array with a few simulated spots so each registered pipeline gets a
   realistic-shaped input. This makes Phase 1 reproducible on CI and on
   the user's laptop.
4. **Tab switching uses offscreen Qt** — sets
   `QT_QPA_PLATFORM=offscreen`. No display required, no real ND2 file
   required. The scenario instantiates `MainWindow`, walks
   `Settings.PAGES` keys via `_navigate()`, times each transition.
5. **One JSON per run** — `profiling/baselines/<label>.json` is the
   single source of truth. The format is stable across phases so we
   can diff `phase_00_baseline.json` against `phase_02_lazy_loading.json`
   later without an ad-hoc parser.
6. **No new dependencies** — `psutil` is already in
   `requirements.txt`. `py-spy`, `snakeviz`, `memory_profiler`, and
   `line_profiler` are documented in `profiling/README.md` as optional
   companions for flamegraph capture but are not imported anywhere in
   the harness.
7. **PySide6, not PyQt6** — Phase 1 doc was written framework-agnostic;
   the harness wires to PySide6 like the rest of ND2Studios.

## What changes for the user

Nothing in the running application. Running ND2Studios via
`python run.py` behaves identically. The harness is invoked manually:

```bash
# Optional: set up a folder with small.nd2 / large.nd2 / small.tif / large.tif
export PROFILING_TEST_DATA_DIR=/path/to/profiling_data

# Capture a baseline
python -m profiling.harness.run_all phase_00_baseline

# Re-capture after Phase 2 work is done
python -m profiling.harness.run_all phase_02_lazy_loading
```

## Acceptance criteria

- [ ] `python -m profiling.harness.run_all` runs end-to-end on a clean
      checkout (with no lab data present) and writes a JSON file. Load
      / scrub scenarios degrade gracefully when no test data is set.
- [ ] Tab-switch scenario runs offscreen, with no display attached.
- [ ] Analysis scenario succeeds for every pipeline currently in the
      registry (Bright/Dark Spots, Histogram Threshold, Tear Detection,
      Manual Mask) using only the synthetic input — Cellpose-dependent
      Nuclei Segmentation is allowed to be skipped if the optional dep
      is missing.
- [ ] JSON contains real numbers for whatever scenarios were able to
      run; system info block records CPU / RAM / platform.
- [ ] No production code outside `nd2studios/utils/` is modified.
- [ ] `nd2studios/utils/profiling.py` imports cleanly without Qt.

## Common pitfalls (from Phase 1 doc, called out here for ND2Studios)

- Cold OS page cache makes the first scrub artificially slow — the
  user should warm up by running the scrubbing scenario twice and
  prefer the second number for "warm" measurements.
- `cProfile` adds 2-5× overhead and biases pure-Python hot paths;
  prefer `py-spy record` for whole-app profiling. The harness uses
  `time.perf_counter` + `tracemalloc` only.
- `app.processEvents()` is required after `setCurrentIndex()` to let
  any deferred work the page schedules (e.g. lazy histogram resample,
  prefetch enqueue) complete before the timer stops.
- The `nd2` library's per-file state is not thread-safe; we open the
  volume on the same thread that reads from it, mirroring how
  `LazyND2Channel.materialize` documents the constraint.

## After this phase

Once `phase_00_baseline.json` is captured and `profiling/REPORT.md`
identifies the actual hot paths, decide whether Phase 2 (Lazy Loading
& Threading) or some other phase should run next. The Phase 1 doc
recommends Phase 2 → 3 → 4 → 5 → 6 → 7, but this is a recommendation,
not an order to follow blindly.
