# V1.71 — Save Data & Crop pipeline-graph nodes

## Goal

Two new **special** pipeline-graph nodes:

1. **Save Data** (`special:save_data`) — a pass-through node that, when a Run
   reaches it, writes the dataset *as it currently is at that point in the
   pipeline* (enhancement recipe + registration + any upstream crop applied) to
   disk. Non-destructive: it side-effects (writes files) and passes the stream
   through unchanged, so it can sit mid-pipeline (e.g. `input → enhance → Save
   Data → analysis`).

2. **Crop** (`special:crop`, *manual mode only for now*) — a pass-through node
   that applies a user-picked rectangular crop to **every downstream node**
   (analysis, tracking, export, Save Data, the viewer overlay). Mirrors the
   Registration node's "crop to common region" mechanism: it publishes a crop
   rect on the record that the page's existing `_crop_rect()` composition picks
   up, so the whole downstream pipeline reads the cropped image with no per-node
   changes.

## Approach

Both are **special** nodes (hardcoded `NodeSpec` factories + `param_specs_for`
branches + `_run_execute_node` dispatch), not plugins, because they do
side-effecting / spatial-scope work rather than transforming a `(T,H,W)` array
in place. Both use `PortType.ANY` in/out so they wire *upstream* of analysis
(like Registration / Checkpoint) and get no rainbow channel port
(`spec_takes_channels` needs `PortType.IMAGE`).

### Save Data
- Reuse `backend/exporters/tiff_exporter.export_tiff_hyperstack(channels,
  enabled, filepath, bit_depth, pixel_size_um)` — it takes exactly the
  `{channel: (T,H,W)}` dict the page's `_processed_channels_for_m` /
  `_materialize_channels_for_m` produce, and writes an ImageJ TZCYX hyperstack
  with pixel-size tags. Also offer an NPZ option (`np.savez_compressed`).
- `_processed_channels_for_m` applies recipe + registration + crop → the "as it
  is here" data. `_materialize_channels_for_m` gives raw + registration + crop.
  A `source` param chooses between them.
- One file per multipoint (`_M01`, `_M02`, …) when *All multipoints* is on or
  the dataset has >1 M; otherwise a single file. Prompt for a folder (like
  `_run_export`).
- Because both channel helpers already route through `_crop_rect()`, a Save Data
  node placed downstream of a Crop node automatically saves the cropped data.

### Crop (manual)
- Hidden `rect` param `(x, y, w, h)` in raw-image px + a `mode` choice
  (`"Manual (draw / enter rectangle)"` only, for now — leaves room for future
  auto/content modes). Picked via a popup **"Pick crop region…"** edit button
  that reuses the existing rich `_show_preview_crop_dialog` (x/y/w/h fields, jog
  pad, live cropped preview) — no new dialog.
- New record field `record._pipeline_crop = (x, y, w, h)`, published by
  `_run_crop` when the Run reaches the node, reset at run start alongside
  `record._registration_crop`.
- New `_pipeline_crop_rect()` helper + third term in `_crop_rect()` and
  `_effective_run_crop()` (intersected with the preview + registration crops via
  the existing `_intersect_crop_rects`). This is the whole "applies to the rest
  of the pipeline" mechanism — every downstream image read already funnels
  through `_crop_rect()`.
- `pixel_size_um` is preserved by a crop (no rescale); only H/W shrink, which
  `_preview_metadata` already overrides from `_crop_rect()`.

## Key decisions

- **Pass-through, not sinks.** Save Data emits `ANY` (unlike the existing
  Export sink) so it can sit mid-pipeline and the run continues. Crop emits
  `ANY` so it wires upstream of analysis.
- **Crop reuses the registration crop plumbing** rather than inventing a new
  path — a third source in `_crop_rect()`. The crop applies only on a Run
  (like the registration common-region crop); the standalone preview-crop tool
  still covers interactive/preview cropping.
- **No new dialog for Crop** — reuse `_show_preview_crop_dialog`.
- **Manual only** — the `mode` param documents the current scope and leaves a
  seam for future automatic crop modes.
