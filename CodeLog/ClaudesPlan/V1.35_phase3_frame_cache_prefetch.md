# V1.35 — Phase 3: Frame Cache & Prefetcher

## Goal

Convert the spare RAM the user has into measurable smoothness on
M / T / Z scrubbing. After this phase, the displayed plane is **never
evicted** while it is on screen, the prefetcher **biases its window in
the direction the user is scrubbing**, and the cache **reports hit /
miss / eviction counters** the next phase can wire into the status bar.

## Where ND2Studios already stands

Phase 3 in the framework-agnostic plan introduces a `FrameCache` and
a `Prefetcher`. ND2Studios shipped both back in V1.17:

| Phase 3 doc concept                                      | Existing ND2Studios equivalent                                                                |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Byte-budgeted LRU cache                                  | `nd2studios.backend.frame_cache.FrameCache` (V1.17)                                           |
| Adaptive RAM budget                                      | `recommended_cache_budget_bytes(reserve_fraction=0.6)` (V1.34)                                |
| Prefetcher thread                                        | `nd2studios.workers.prefetch_worker.PrefetchManager` (V1.17)                                  |
| Cache check on slider event                              | `MultiAxisViewer._compose_current_frame` (V1.17)                                              |
| Foreground IO worker for cache misses                    | `nd2studios.utils.threading.IOWorker` (V1.34)                                                 |
| Stale-display-request dropping via `request_id`          | `MultiAxisViewer._latest_request_id` (V1.34)                                                  |
| Pre-cache neighbor warming                               | `PrefetchManager.request_neighbors(m, t, z, ±5)` (V1.17)                                      |

That leaves **four** gaps specific to Phase 3.

### Gap 1 — the prefetcher is direction-blind

`PrefetchManager.request_neighbors` queues a *symmetric* ±5 window on
T (or Z when T is degenerate). When the user is scrubbing forward at
10 fps, half of every prefetch budget is spent on planes the user has
already passed and will not revisit. The Phase 3 doc's central new
idea is **velocity-aware prefetch**: bias the window forward when
moving forward, backward when moving backward, symmetric only when
stopped. Closing this gap roughly doubles the effective lookahead on
fast scrubs without enlarging the queue.

### Gap 2 — the displayed plane can be evicted

`FrameCache` evicts strictly by LRU. If the prefetcher is mid-burst
filling neighbors of the *previous* coords and the user lands on a
coord whose plane was put into the cache early in the gesture, that
plane can be evicted by its own neighbors before the next gesture.
The Phase 3 doc fixes this with **pinning**: the currently-displayed
keys are excluded from eviction. ND2Studios needs the same — one pin
per enabled channel of the active `(m, t, z, z_mode)`.

### Gap 3 — cached arrays are not marked immutable

`FrameCache.put` stores whatever array the caller hands in. Nothing
prevents the GUI thread from mutating that array in place; if it does
(an in-place LUT, a draw overlay, anything), the next cache hit sees
the mutated copy. Phase 3 doc's fix: `arr.flags.writeable = False` on
put. Cheap, defensive, no behavior change for code that does the right
thing.

### Gap 4 — no cache telemetry

Today there is no way for the viewer, the profiling harness, or a
future status-bar tooltip to ask the cache how it is doing. Phase 3
adds a `CacheStats` dataclass tracking hits, misses, evictions, current
bytes, and peak bytes; the cache itself updates it under the existing
lock so callers can read it from any thread.

## Approach

1. **Extend `frame_cache.py` in place.** Add `CacheStats`, `pin(key)`,
   `unpin(key)`, `is_pinned(key)`, `set_max_bytes(n)`, and the
   `stats: CacheStats` attribute. Update `get` / `put` to record hits
   / misses / evictions / byte totals. Make eviction skip pinned
   entries; break out of the eviction loop when only pinned entries
   remain (otherwise we'd infinite-loop a full-of-pins cache). Mark
   inserted arrays `writeable=False` on `put`. The pre-V1.35 method
   signatures stay the same so no caller has to change just to compile.

2. **Make `PrefetchManager` velocity-aware.** Track the previous
   `(m, t, z, z_mode)` and its `time.perf_counter()` timestamp. On
   each `request_neighbors` call, compute `dt`, derive a T-axis
   velocity in planes/sec, and bias the T window asymmetrically:

   - velocity ≥ +1 planes/sec → `[t - 2, t + radius_t]`
   - velocity ≤ -1 planes/sec → `[t - radius_t, t + 2]`
   - otherwise → symmetric `[t - r, t + r]` with `r = radius_t // 2`

   Z-axis fallback (single-T volumes) keeps the existing symmetric
   policy — Z scrubbing in this app is rare enough that hand-tuning
   it is gratuitous.

3. **Make `radius_t` adaptive.** Pass a `radius_t` to
   `PrefetchManager.__init__`; pick it in `MultiAxisViewer.set_volume`
   from available RAM via `resources.detect()`:

   - `< 2 GB free`  → `radius_t = 2`
   - `< 8 GB free`  → `radius_t = 4`
   - otherwise      → `radius_t = 8`

   Same three-tier table the Phase 3 doc names. Old default of 5
   stays as the constructor default so any unit tests / scripts that
   build the manager directly still get a sane value.

4. **Pin the currently-displayed keys in the viewer.** After
   `_compose_current_frame` collects a full set of channel sources,
   it pins every `(c_idx, m, t, z, z_mode)` it just used and unpins
   the previous set. The `_pinned_keys: set[tuple]` lives on the
   viewer instance. `set_volume` / `set_channels` / `_teardown_io_worker`
   clear it; `_frame_cache.clear()` will also clear pins via the new
   `FrameCache.clear()` behavior.

5. **Expose cache stats.** Add a tiny `cache_stats_text()` helper on
   the viewer that returns
   `"Cache: 612 / 6320 MB · hit 73.2% · evictions 14"`. Phase 4 (or
   a debug overlay) can hook this into a status bar; for V1.35 it is
   only used by the profiling harness so we have a number to point
   at when we say "Phase 3 worked."

6. **Profile.** Re-run `python -m profiling.harness.run_all phase_03_cache`
   (or add the scrub scenario if it doesn't exist yet) and record the
   new baseline. We expect scrub miss rate to drop and cache peak bytes
   to climb closer to the configured budget.

## Architectural decisions

1. **No new priority queue.** The Phase 3 doc's reference code uses
   one `PriorityQueue` with `PRIORITY_DISPLAY < PRIORITY_NEIGHBOR <
   PRIORITY_FAR`. ND2Studios already separates display vs. neighbor
   reads onto two threads (`IOWorker` and `PrefetchManager`) — the
   OS read-ahead layer plus the dedicated threads give us the same
   ordering for free. Collapsing them would mean rewriting both;
   no profile-driven win justifies that diff.

2. **Velocity-tracking lives in the prefetcher, not the viewer.**
   The viewer already calls `request_neighbors` at the end of every
   `_compose_current_frame`; if the prefetcher does its own
   timestamping the viewer has nothing new to plumb. Phase 5's
   analysis worker and Phase 6's pipeline scheduler will likely
   reuse the velocity estimate if/when they appear; centralizing it
   here makes that easy.

3. **Pin granularity is per-channel-plane, not per-composite.** The
   cache stores per-channel planes; the displayed image is a composite.
   Pinning the composite would mean caching it (which Phase 3 doc
   explicitly warns against — composites multiply RAM by channel
   count). So we pin every `(c_idx, m, t, z, z_mode)` that contributed
   to the current frame. On a 4-channel scrub that's 4 pinned entries
   at a time, which is fine.

4. **Stats are a snapshot, not an event stream.** `CacheStats` is a
   mutable dataclass updated under the cache lock; callers read the
   current value. No signals, no listeners, no per-event callbacks.
   The profiling harness samples it; a future status bar would poll
   on a 1 Hz `QTimer`. Keeping it passive avoids cross-thread Qt
   plumbing for what is fundamentally a debug surface.

5. **Pre-V1.35 callers unchanged.** Every constructor argument added
   in this phase has a default. Every method added is new. Tests
   and scripts that built a `FrameCache(max_bytes=...)` or a
   `PrefetchManager(reader_factory, cache, channels)` keep working.

## What does *not* change

- The `IOWorker` and its `PlaneRequest` queue stay exactly as V1.34.
- The viewer's debounce timers (50 / 80 ms on T / Z / M) stay.
- `MultiAxisViewer._compose_current_frame`'s cache-miss path still
  routes through `IOWorker.submit` — pinning happens around it, but
  the request flow is unchanged.
- `LazyND2Volume`, `LazyMultiFileND2Volume`, and
  `LazyMultiFileTIFFVolume.get_frame` keep the same contract.
- The flat-channel `set_channels` path (Recipe page) gets the same
  pinning treatment but no prefetcher (there is no disk read on this
  path — the channels are already in RAM as `(T, H, W)` arrays). The
  pin/unpin code is shared because it costs nothing on this path.

## Acceptance criteria

- [ ] Visiting a plane, scrubbing away, and visiting it again hits
      the cache (`stats.hits` goes up) as long as it was not evicted
      to make room for prefetches. On a 6 GB budget with the lab's
      typical 4-channel 30-T ND2, the entire 120-plane working set
      fits and second visits are instant.
- [ ] During a forward T scrub, the prefetcher's queued keys cluster
      ahead of the current position. Verifiable by adding a debug
      print in `PrefetchManager.request_neighbors` or by watching
      `stats.current_bytes` climb only in the forward direction.
- [ ] The currently-displayed plane is never evicted while it is on
      screen — confirmable by setting `max_bytes` artificially low
      (e.g. 128 MB) and watching `cache.is_pinned(displayed_key)`
      stay True while `stats.evictions` ticks up around it.
- [ ] Mutating a cached array (e.g. `cache.get(k)[:] = 0`) raises
      `ValueError: assignment destination is read-only`.
- [ ] `cache_stats_text()` returns a string that includes hit rate
      and current/max bytes; the values are non-zero after a scrub.
- [ ] `set_volume(new_vol)` and `set_volume(None)` both leave the
      cache with `len(cache) == 0` and `stats.current_bytes == 0`
      and `is_pinned(k) is False` for every previously displayed key.
- [ ] `python -m profiling.harness.run_all phase_03_cache` runs
      end-to-end and emits a snapshot whose scrub miss rate is lower
      than the Phase 2 snapshot collected in V1.34.

## Common pitfalls (called out for ND2Studios specifically)

- **Pinning the wrong key after channel toggle**: if the user disables
  a channel, that channel's keys should be unpinned. The simplest fix
  (and what the implementation does) is to recompute the pinned set
  from `sources` at the end of every `_compose_current_frame` — the
  set just *replaces* the previous set, no per-event delta tracking.
- **Pin leaks across files**: a previous file's keys would technically
  fit the LRU key shape but would never re-appear on the cache. We
  drop the entire pinned set in `set_volume` / `set_channels` /
  `_teardown_io_worker` (the same teardown points that clear the
  cache itself).
- **`writeable=False` on a view**: the prefetcher's
  `frame.squeeze()` may return a view of the underlying ND2 array.
  Setting `writeable=False` on a view freezes only the view; the
  underlying array remains writeable. That is fine for our use —
  what we care about is callers not mutating the cached *handle*.
  If a downstream consumer wants a mutable copy it should
  `np.array(cache_hit)` explicitly.
- **Velocity sign convention**: T increases over time when the user
  drags right on the slider; that is "forward". `velocity_t > 0`
  means forward. A negative slider step (user dragged left) means
  `velocity_t < 0`. Verify against the slider's value range, not
  against any timestamp ordering.
- **`PrefetchManager.cancel_all` does not reset the focus history**.
  That is intentional — if the user releases the mouse mid-scrub
  the previous velocity is still the best estimate of intent. The
  history only resets when a new `reader_factory` is installed,
  i.e. `set_volume()` builds a new `PrefetchManager`.
- **`set_channels` (Recipe page) has no prefetcher** — calling
  `request_neighbors` from `_compose_current_frame` is gated on
  `self._prefetch is not None`. That gate stays; do not add a
  prefetcher for the in-RAM channel path.

## After this phase

Phase 4 (pyqtgraph display) is the next bottleneck. With cache and
prefetcher now well-behaved, the per-frame cost is dominated by the
NumPy → QImage path in `ImageCanvas.set_image`. Phase 4 will replace
that with a `pyqtgraph.ImageItem` that takes a uint16 ndarray plus
LUT parameters directly, pushing the per-frame work to the GPU and
making LUT/contrast changes free. The cache stats added in this
phase will be the way we *prove* the bottleneck has shifted from
I/O to display.
