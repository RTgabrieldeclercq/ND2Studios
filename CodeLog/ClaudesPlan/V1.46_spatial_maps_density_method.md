# V1.46 — Spatial maps: compute every field the way cell density is computed

## Goal

Fix the Cell-Tracker spatial maps so **every** field is formed from the recorded
cells the same way the (correct) **cell density** field is, instead of by
interpolation. Reported symptom: "all fields other than cell density are
incorrectly computed."

## Investigation — how density is formed vs. the rest

`backend/celltracker/fields.compute_spatial_fields` computed two ways:

- **Density (correct):** bins each recorded cell's centroid into a grid bin —
  `density[int(y/step), int(x/step)] += 1` — then Gaussian-smooths. The value at
  every grid node is built from the cells actually present there.
- **Everything else (wrong):** `mean_area`, `intensity`, `fold_change`,
  `self_fold`, `velocity_y/x`, `speed`, `divergence`, `curl`, and arbitrary
  measurement columns used `scipy.interpolate.griddata`. That triangulates the
  centroids, interpolates a value across the *whole* grid, then pads everything
  outside the convex hull with the single global frame mean
  (`nan_to_num(..., nan=np.nanmean(values))`). Result: a blanket field that
  invents values in empty space and washes out local structure — not a map of the
  recorded data. (It also required ≥4 cells just to build a triangulation.)

The two are not arbitrarily different: density is the **denominator** of a
kernel-weighted (Nadaraya–Watson) local mean. So the fix is to make every
value-bearing field that same local mean.

## Approach

Generalise the density binning to a **Gaussian-weighted local mean**:

1. Bin the per-cell value-sum and the cell count into grid bins (centroid →
   `(int(y/step), int(x/step))`), skipping out-of-grid / non-finite values.
2. Smooth both the value-sum and the count with the **same** Gaussian.
3. Field = `smoothed_sum / smoothed_count` where cells lie within the kernel,
   else a fill (`NaN` for scalar fields; `0` for the velocity field so its
   `divergence` / `curl` gradients stay finite).

Density stays exactly as-is (it is the smoothed count = the shared denominator).

## Follow-up — restrict value fields to the cell footprint

First cut still showed value fields in empty space. Root cause: a normalised local
mean (`sum / count`) does **not** fade away from cells the way the density *count*
does — numerator and denominator decay together under the Gaussian, so the ratio
holds the cell's value flat across the **whole** kernel (≈ `4·sigma` ≈ 8 grid bins
≈ 160 px) and bridges the gaps between neighbours. (Density / intensity / fold-
change looked fine: a count self-masks by fading, and the channel-intensity path
reflects the dark background.)

Fix: add `cell_footprint(cy, cx, grid_shape, grid_step, dilate=1)` — boolean mask
of bins that actually contain an object, dilated by one bin for sub-grid coverage.
`_binned_mean_field` takes an optional `mask` and sets everything outside it to
`fill`. `compute_spatial_fields` masks `mean_area` / `intensity` / `fold_change`
to the all-cell footprint; velocity is binned filled (`0`) so divergence/curl
gradients stay finite, then `velocity_*` / `speed` / `divergence` / `curl` are
masked to the *velocity* footprint (cells tracked into the previous frame).
`SpatialMapsPanel._bin_value_field` does the same for `self_fold` / columns. The
gridded-velocity overlay (`_paint_vectors_overlay`) `nan_to_num`s the now-`NaN`
dead space before drawing. Density is left unmasked (it fades on its own).

## Decisions

- **Mask, don't rely on kernel reach.** Kernel-reach NaN alone left a 160-px
  plateau around every cell; the footprint mask makes locality independent of
  `sigma`, so smoothing controls smoothness without leaking values into empty
  regions or across inter-cell gaps.
- **NaN vs. fill outside the data.** Scalar fields are `NaN` outside the footprint
  (rendered transparent by `pcolormesh`; quiver skips NaN arrows). The velocity
  grid is computed `fill=0.0` for the gradient pass, then NaN-masked for display.
- **Density unmasked.** It is a count that vanishes in empty space, so it
  self-masks; the user confirmed density already looked correct.
- No schema/API change — same field keys, same `FIELD_OPTIONS`, same call sites.
