# V1.39 — Phase 7: Optional GPU Acceleration & Multi-Resolution Pyramids

## Goal

Make ND2Studios *hardware-adaptive*. On a laptop with no CUDA device the
binary behaves exactly as it does in V1.38. On the McGhee Lab workstation
with an NVIDIA card and CuPy installed, three things become available:

1. **GPU dispatch for hot analysis ops** — DoG/LoG response,
   `gaussian_filter`, `threshold_otsu`, and the tear-detection
   `gaussian + log + threshold_otsu` chain route through CuPy + `cucim`
   when a runtime feature flag is on, with a graceful fall-through to
   scikit-image / scipy when the GPU is absent or out of memory.
2. **Multi-resolution image pyramids** — a per-source workspace artifact
   (`pyramid.zarr`) the `MultiAxisViewer` reads from when zoomed out
   far enough that the full-resolution plane wastes texture bandwidth.
   Built once in the background after import, reused on every later
   open of the same file via the V1.38 `Session` hash key. Analysis
   never reads pyramids — full-resolution stays the source of truth.
3. **Performance settings panel** — a small page on the existing
   Sidebar's bottom controls (or a modal launched from a new
   `⚙ Performance` button) where the user can toggle "Use GPU
   acceleration" and "Build multi-resolution pyramids" without
   restarting the app.

GPU work is alluring but rarely the binary bottleneck. By V1.38, ND2Studios
is fast because of Phases 1–6. This phase is the difference between *fast*
and *fast on huge stacks* — and on machines where the speedup would be
zero, it adds zero overhead.

## Where ND2Studios already stands

The generic Phase 7 doc assumes a green-field viewer and a single
"analysis" tab; ND2Studios's shape is different:

- **The display path is already GPU-side (V1.36).** `GpuImageCanvas`
  uses pyqtgraph's `pg.ImageItem` with per-channel LUTs and
  `CompositionMode_Plus`. Channel additive compositing, LUT,
  contrast/levels, and gamma-less display all happen on the Qt
  raster engine. Phase 7's GPU dispatch is *not* about display — it
  is about analysis ops and pyramid generation.
- **Frame cache is RAM-tier, Phase-3 sized.** A single `(c, m, t, z,
  z_mode)` key feeds a byte-budgeted LRU. Phase 7 extends the key by
  one optional `level` slot so the viewer can prefetch and pin
  downsampled planes without invalidating the V1.35 stats / pinning
  contract. When pyramids are off, `level=0` for every key and the
  cache behavior matches V1.38 exactly.
- **The V1.38 `Session` is the natural pyramid host.** Each source
  file already has its own per-hash directory. A `pyramid.zarr`
  artifact slots in as a third stage record next to `recipe` and
  `analysis:<pipeline>` — no manifest schema migration needed, just
  one more key in `stages`. The hash key carries cross-session
  resumption for free: the second time the user opens a 30 GB ND2
  file, the pyramid is already on disk.
- **Cellpose is already a soft dep.** `NucleiSegmentationPipeline`
  guards its import with `importlib.util.find_spec("cellpose")` and
  raises a friendly ImportError when called without it. We do *not*
  need to introduce a new opt-in plugin path; we **do** need to flip
  the `gpu=False` argument on `models.Cellpose(...)` when the user
  has enabled GPU mode in Performance settings.
- **StarDist is intentionally out of scope.** The McGhee Lab pipeline
  does not use it; tacking on a second ML framework that also wants
  GPU memory (TensorFlow vs. Cellpose's PyTorch) creates dependency
  pain without delivering a feature anyone uses. If a user asks for
  StarDist later, we add it as its own analysis plugin with the same
  soft-import pattern Cellpose uses today.
- **`cucim`, not raw CuPy.** ND2Studios's hot ops are all
  scikit-image / scipy band-pass filters. `cucim.skimage.filters`
  has matching shapes and signatures for `gaussian`,
  `gaussian_filter`, `gaussian_laplace`, `threshold_otsu`, plus the
  registration / measure subpackages we will not need here. CuPy is
  pulled in transitively by `cucim`; we never import bare `cp` in
  analysis code paths. The `xp` abstraction in the generic doc
  collapses to a `compute.gpu.ops` module of named functions.
- **No napari pyramid format.** The generic doc proposes a 6-D
  `(T, M, Z, C, Y, X)` Zarr; ND2Studios's viewer is always reading a
  single channel-frame at the active `(c, m, t, z, z_mode)`. A
  per-level `(M, T, Z, C, H/2^L, W/2^L)` layout matches the
  `LazyND2Volume.get_frame` signature so the read site is identical
  except for one indexing argument.

The takeaway: Phase 7 for ND2Studios is **lean and additive**. A new
`compute/gpu/` module (detect, array, ops), a new `pipeline/pyramid/`
file with a `PyramidStage` + `PyramidReader`, four touchpoints
(`MainWindow`, `MultiAxisViewer`, the spot/tear pipelines, the
Cellpose pipeline), and a tiny Performance settings dialog. No
rewrites; no GUI flow change visible to the user beyond a one-line
status note ("GPU: NVIDIA RTX A4000, 16.0 GB") at startup when CuPy is
present.

## Architecture

```
nd2studios/compute/
├── gpu/
│   ├── __init__.py
│   ├── detect.py            # gpu_status() + log_gpu_status() at startup
│   ├── array.py             # configure(), is_gpu_enabled(), to_xp/to_numpy
│   └── ops.py               # gaussian, gaussian_filter, gaussian_laplace,
│                            # threshold_otsu — all numpy/cupy aware
└── ...

nd2studios/pipeline/
├── stages/
│   ├── pyramid_stage.py     # PyramidStage + PyramidReader
│   └── ...
└── ...
```

The display layer (`widgets/gpu_image_canvas.py`,
`widgets/multi_axis_viewer.py`) does not import from `compute/gpu/`.
The display GPU path (pyqtgraph) and the analysis GPU path (CuPy) are
intentionally independent — one going down does not take the other
with it.

### `compute/gpu/detect.py`

```python
def gpu_status() -> dict:
    """Return {available, reason, device_name, memory_gb}.

    Always cheap; safe to call from import time. Never raises — every
    failure path returns ``available=False`` with a human-readable
    reason so the Performance panel can surface it verbatim.
    """

def log_gpu_status() -> None:
    """Emit one log line summarizing GPU availability. Called from
    ``__main__.py`` after Qt is up so the message lands in the same
    sink as the rest of ND2Studios's startup output.
    """
```

Detection guards every `import cupy` behind a `try/except ImportError`
and every `cp.cuda.*` call behind a broad `except Exception` — the
NVML / driver layer can raise non-Exception errors (`CUDARuntimeError`)
that need to be swallowed without dragging the rest of the app down.

### `compute/gpu/array.py`

Module-level `_USE_GPU: bool` (default False). Three callers:

```python
configure(use_gpu: bool) -> bool   # returns the effective value
is_gpu_enabled() -> bool           # reads _USE_GPU
to_xp(arr)                          # numpy → cupy when enabled, else identity
to_numpy(arr)                       # cupy → numpy, else identity
```

`configure()` is the only mutator. Called once by the Performance
settings dialog when the user flips the checkbox; the next analysis
job sees the new value. We never run two analysis jobs with different
backends concurrently because the V1.37 `JobRunner` serializes the
`analysis_preview` and `analysis_commit` queues by coalescing key.

### `compute/gpu/ops.py`

Wraps the four scikit-image / scipy ops that V1.33's profiling baseline
flagged as analysis hotspots:

```python
def gaussian(image, sigma) -> np.ndarray:
    """skimage.filters.gaussian-compatible; preserve_range=True."""

def gaussian_filter(image, sigma) -> np.ndarray:
    """scipy.ndimage.gaussian_filter-compatible (used by spots DoG)."""

def gaussian_laplace(image, sigma) -> np.ndarray:
    """scipy.ndimage.gaussian_laplace-compatible (used by spots LoG)."""

def threshold_otsu(image) -> float:
    """skimage.filters.threshold_otsu-compatible."""
```

Every function:
1. Checks `is_gpu_enabled()` and array size (skip GPU for arrays
   smaller than 256×256 — host↔device transfer dominates).
2. On the GPU branch: `to_xp(image)`, call `cucim.skimage.filters.<op>`,
   `to_numpy(result)` before returning. The host↔device boundary stays
   inside this module so callers always see numpy.
3. On any GPU branch failure (`cupy.cuda.memory.OutOfMemoryError`,
   missing `cucim`), log a warning *once per op* and fall back to the
   CPU implementation. The warning carries the op name so the user
   knows which call to investigate.

The "log once" pattern is a class-level set of names that have already
fired; subsequent failures of the same op silently fall through. This
is critical because a Cellpose run on the same machine can monopolize
the GPU memory pool — we do not want a flood of warnings during a
single segmentation job.

### `pipeline/stages/pyramid_stage.py`

`PyramidStage` is the third stage type after `RecipeStage` and
`AnalysisStage`. The on-disk layout sits alongside them:

```
~/.nd2studios/workspace/sessions/<hash>/
├── manifest.json
├── recipe/
├── analysis/
└── pyramid/
    └── pyramid.zarr/      # ZarrGroup with one ZarrArray per level
        ├── 0/             # full-resolution mirror; we DO NOT write this —
        │                  # the source ND2 is the canonical level 0.
        ├── 1/             # H/2 × W/2 per plane
        ├── 2/             # H/4 × W/4
        ├── 3/             # H/8 × W/8
        └── 4/             # H/16 × W/16
```

Level 0 is omitted; the viewer always reads the full-resolution plane
from the existing `LazyND2Volume`. The pyramid only stores levels
≥ 1, which keeps the disk footprint to ≈ 1/4 + 1/16 + 1/64 + 1/256 ≈
33 % of source size rather than ≈ 133 %. This is a deliberate
divergence from the generic Phase 7 doc — ND2Studios already has a
fast level-0 reader (`LazyND2Volume.get_frame`), so we do not need to
copy the source into Zarr to keep level-0 reads fast.

Each level is a `(n_m, n_t, n_z, n_channels, H_L, W_L)` Zarr array
chunked `(1, 1, 1, 1, H_L, W_L)` — single-plane chunks, matching the
viewer's read pattern. Compressor: Blosc zstd-3 (Zarr 3 default).

```python
class PyramidStage(PipelineStage):
    name = "pyramid"

    def __init__(self, session: Session, *, n_levels: int = 5,
                 downscale: int = 2, min_dim: int = 64):
        ...

    def build(
        self,
        volume,
        progress_cb: Callable[[int], None] | None = None,
        cancel_cb: Callable[[], bool] | None = None,
    ) -> StageRecord:
        """Build the pyramid from a volume. Idempotent: returns the
        existing record if the manifest says it is already complete."""

    def reader(self) -> Optional[PyramidReader]:
        """Open the pyramid for reading. Returns None if not built or
        if zarr is missing. The caller is expected to ``close()`` it
        when done (no-op when zarr arrays are used directly)."""

class PyramidReader:
    """Indexable per-level reader.

    Provides ``get_frame(level, c, m, t, z, z_mode='none')`` matching
    the ``LazyND2Volume.get_frame`` signature so the viewer can
    A/B-test the two on the same code path. ``pick_level_for_viewport(
    viewport_screen_px, image_pixels_visible)`` returns the smallest
    level whose width is still ≥ viewport_screen_px.
    """
```

The build job is a regular Phase 5 `AnalysisJob` (`BuildPyramidJob` in
`compute/pipeline_jobs.py`) so it gets cancellation, progress
reporting, and coalesce-keying for free. The Performance settings
button "Rebuild pyramid" submits a new job with key
`"pyramid_build"`; submitting it twice cancels the first.

### Pyramid → cache key extension

`MultiAxisViewer._frame_cache` uses
`(c_idx, m, t, z, z_mode)`. Phase 7 promotes this to
`(level, c_idx, m, t, z, z_mode)` with `level=0` meaning "read from
`LazyND2Volume.get_frame` (no pyramid)" and `level>=1` meaning "read
from `PyramidReader.get_frame(level, ...)`". The cache is shared
across levels — same byte budget, levels compete for residency, but
pyramid planes are tiny so a level-3 plane is ~64× smaller than a
level-0 plane and trivially fits.

`PrefetchManager` extends its request shape with an optional `level`
argument. When pyramids are off, the prefetcher uses `level=0` and
behaves exactly like V1.38.

### Viewer integration

`MultiAxisViewer` gets one new field, `_active_level: int = 0`, set by
a new `_choose_active_level()` helper called from
`_on_viewport_changed()`. The viewport-change signal is already
emitted by pyqtgraph's `ViewBox.sigRangeChanged`; we just need to
connect it. When `_active_level` changes:

1. Bump `_request_counter` so any in-flight IO worker plane for the
   old level is dropped on arrival (the existing
   `_latest_request_id` gating handles this).
2. Call `_do_refresh()`. The render path looks at `_active_level` and
   either calls `LazyND2Volume.get_frame` (level 0) or
   `self._pyramid_reader.get_frame(level, ...)`.
3. Re-pin the keys at the new level; unpin the old.

The pyramid is **optional and falls back to level 0**:

- No `Session` (rollback env var, missing workspace): always level 0.
- `Session` exists but `pyramid` stage is not committed: level 0, plus
  a one-shot status-bar note ("Building pyramid in background...")
  while `BuildPyramidJob` runs.
- `Session` exists, pyramid committed but `zarr` missing in this
  environment: level 0, status-bar note ("Pyramid unavailable: zarr
  not installed"). This matches the V1.38 storage fallback —
  pyramids are zarr-only because NPZ cannot stream sub-chunks.

When the user pans/zooms onto a new viewport rect, the viewer asks
the reader for the best level *for the visible image-pixel extent
mapped to screen pixels*, not the device-pixel-ratio-adjusted
screen size. Picking by extent makes the choice DPI-independent.

### What is *not* on the GPU path

To keep scope honest, the following stay on CPU:

- **ND2 / TIFF decoding.** The `nd2` library is CPU-only and so is
  `tifffile`. The pyramid builder reads with the existing CPU reader
  and only downsamples on GPU when enabled.
- **Display compositing.** Already GPU (pyqtgraph) since V1.36.
- **`gaussian_filter` outputs feeding extrema detection** (peaks,
  regionprops, watershed). CPU-side; the GPU is for the band-pass
  responses themselves, where the cost per pixel is highest.
- **Histogram computation** (`compute_histogram`). It is already a
  single `np.bincount` and faster on CPU than any GPU dispatch for
  the array sizes ND2Studios deals with.
- **Recipe enhancement plugins.** Most are OpenCV or skimage; they
  are not on the V1.33 baseline's hot list. Adding GPU paths here is
  a maintenance tax with no payoff — explicitly out of scope.

## Wiring into the existing flow

Six touchpoints, all small.

### 1. `compute/gpu/` package — new

Three files (`detect.py`, `array.py`, `ops.py`) as above. Public
re-exports in `compute/gpu/__init__.py`:

```python
from .array import configure, is_gpu_enabled, to_numpy, to_xp
from .detect import gpu_status, log_gpu_status
from .ops import gaussian, gaussian_filter, gaussian_laplace, threshold_otsu
```

`compute/__init__.py` does *not* re-export these — callers that want
GPU-aware ops import from `nd2studios.compute.gpu` explicitly so the
intent is visible at the import site.

### 2. `pipeline/stages/pyramid_stage.py` — new

`PyramidStage` + `PyramidReader` + a `default_pyramid_levels()`
helper that picks `n_levels` based on the source dimensions
(`int(log2(max(H, W) / 256))` clamped to `[2, 6]`).

`pipeline/__init__.py` re-exports `PyramidStage` so
`MainWindow.pyramid_stage()` matches the existing
`recipe_stage()` / `analysis_stage()` pattern.

### 3. `compute/pipeline_jobs.py` — `BuildPyramidJob`

```python
class BuildPyramidJob(AnalysisJob):
    """Builds a pyramid for a volume in the background.

    Coalesce key: ``"pyramid_build"``. Submitting again cancels the
    in-flight job; this matches the V1.37 analysis preview/commit
    pattern and is how the Performance dialog's "Rebuild" button
    interrupts a half-built pyramid.
    """
```

Returns the `StageRecord` so the `MainWindow.job_done` slot can
update the status bar with `"Pyramid built: 4 levels, 312 MB"`.

### 4. `core/main_window.py` — Performance dialog + GPU log + pyramid hook

Three additions:

1. **`log_gpu_status()` at app startup** — call it from `__main__.py`
   right after `QApplication` is constructed but before the first
   page; emits `"GPU available: ..."` / `"GPU not available: ..."`
   into the same logger ND2Studios already uses. This is also where
   `compute.gpu.array.configure(False)` runs to fix the initial state.
2. **`pyramid_stage()` accessor** mirroring `recipe_stage()` /
   `analysis_stage()`. Returns `None` when `self.session is None` or
   `zarr` is missing.
3. **Performance settings modal** — a new
   `_open_performance_settings()` slot wired to a `⚙` button in the
   sidebar's lower section (next to "New / Save / Load"). The modal
   has two checkboxes and one button:
   - `[x] Use GPU acceleration (NVIDIA RTX A4000, 16.0 GB)` — label
     comes from `gpu_status()`; checkbox is disabled with a "GPU
     not available: <reason>" tooltip when CuPy is missing.
   - `[x] Build multi-resolution pyramids on import` — persisted to
     `Settings.BUILD_PYRAMIDS` (a new module-level bool; persistence
     across launches is out of scope for V1.39).
   - `Rebuild pyramid for current file` — submits `BuildPyramidJob`
     for the active session. Disabled when `self.session is None`.

### 5. `pages/import_page.py` — kick off `BuildPyramidJob`

After `_attach_workspace_and_maybe_resume` succeeds, queue a
`BuildPyramidJob` if (a) `Settings.BUILD_PYRAMIDS` is True, (b) the
session exists, (c) `zarr` is installed, and (d) the pyramid is not
already committed in the manifest. The submission is fire-and-forget
— the user does not have to wait. The status bar shows
`"Building pyramid (level 1/4)..."` from the job's progress
callback; when done, `_status_text` flips to
`"Pyramid built: 4 levels"`.

The Recipe and Analysis pages remain pyramid-unaware. Pyramids are
only for the multi-axis viewer's *display*, never for analysis input.

### 6. `widgets/multi_axis_viewer.py` — viewport-aware level pick

Three small additions:

- `attach_pyramid(reader: PyramidReader)` — called by the Import page
  (and by `MainWindow._on_experiment_changed` for `.nd2s` reloads
  where a workspace also exists). Stores the reader and connects
  `self.canvas._viewbox.sigRangeChanged.connect(self._on_viewport_changed)`.
- `_choose_active_level()` — reads the current view rect width in
  image pixels and the viewport widget width in screen pixels;
  picks the smallest pyramid level whose width is still ≥ the
  screen extent.
- `_do_refresh()` and the prefetch path — the cache key extends to
  `(level, c, m, t, z, z_mode)` and the read site dispatches to
  `volume.get_frame(...)` for level 0 or `reader.get_frame(...)`
  for level ≥ 1.

When the pyramid is not attached (`self._pyramid_reader is None`),
all of this code is dead — `_choose_active_level` returns 0
unconditionally and the cache key's level slot is always 0. The V1.38
behavior is therefore byte-identical.

### 7. Hot analysis backends — soft GPU dispatch

The two callers that benefit measurably:

- `backend/analysis/spots/scale_space.py` — replace
  `scipy.ndimage.gaussian_filter` and `gaussian_laplace` with
  `compute.gpu.ops.gaussian_filter` and `gaussian_laplace`. Same
  signatures; on a CPU-only machine they pass straight through.
- `backend/analysis/tear_detection.py` — replace
  `skimage.filters.gaussian` and `threshold_otsu` with
  `compute.gpu.ops.gaussian` and `threshold_otsu`.

`nuclei_segmentation.py` flips `gpu=False` to
`gpu=compute.gpu.array.is_gpu_enabled()` on the `models.Cellpose(...)`
call. Cellpose handles its own CUDA initialization; we do not feed it
through `compute.gpu.ops`.

`backend/analysis/histothresh/` is unchanged — its hot path is the
histogram, which is already a `np.bincount` and not GPU-eligible.

### 8. `__main__.py` — startup log

After `QApplication`, before `MainWindow`:

```python
from nd2studios.compute.gpu import log_gpu_status, configure
configure(False)  # default off until user opts in via Performance dialog
log_gpu_status()
```

That is the entire startup change. No `Settings` mutation, no signal
wiring. The dialog handles the on/off flip later.

## Acceptance criteria

- [ ] On a machine **without** CuPy installed, `python -m nd2studios`
  starts identically to V1.38 — same log lines plus one
  `"GPU not available: cupy not installed"` info line, no warnings,
  no slower paths.
- [ ] On a machine **with** CuPy + `cucim` installed and a working
  CUDA device, the Performance dialog's "Use GPU acceleration"
  checkbox becomes interactive, and flipping it on causes the next
  Bright/Dark Spots preview to run on the GPU. A measurable
  speedup is observed on a 2048² frame (compare with the V1.33
  profiling harness; the spots DoG response should drop to ≤ 50 %
  of CPU time).
- [ ] Flipping GPU mode off in the Performance dialog does *not*
  require a restart; the next preview/commit runs on CPU.
- [ ] Triggering `cupy.cuda.memory.OutOfMemoryError` (e.g. by setting
  `CUPY_GPU_MEMORY_LIMIT=128mib`) during a commit job logs a
  single warning and falls back to CPU for the failing op — the
  commit completes with the same `AnalysisResult` as the pure-CPU
  baseline.
- [ ] Importing a file with `Settings.BUILD_PYRAMIDS = True` and
  `zarr` installed queues a `BuildPyramidJob`. The progress bar
  reflects the job; the GUI remains responsive (slider scrubbing
  works at level 0 while the pyramid is building).
- [ ] After the pyramid is built, zooming out so that the visible
  image-pixel extent is ≥ 4× the viewport's screen width causes the
  cache key to switch to `level >= 1`. A debug overlay
  (or the `cache_stats_text()` already returned by the viewer)
  confirms it.
- [ ] Analysis pipelines run on full-resolution data regardless of
  the active display level. Verify by capturing the
  `AnalysisResult.label_masks` shape: it always matches
  `(n_t, source_H, source_W)`.
- [ ] Re-opening the same ND2 file in a fresh process finds the
  workspace's `pyramid.zarr` and uses it without rebuilding —
  `manifest.json["stages"]["pyramid"]["committed_at"]` is set, and
  no `BuildPyramidJob` is submitted.
- [ ] `ND2_DISABLE_GPU_ANALYSIS=1` reproduces V1.38 behavior for
  analysis. `ND2_DISABLE_PYRAMIDS=1` skips the build step at import
  and forces `_active_level = 0` everywhere.
- [ ] Total RSS across the workflow (Import → Recipe → Analysis →
  Results) does not grow monotonically beyond the V1.38 baseline.
  The pyramid build does spike RAM briefly while a level is
  computed but releases it on completion of that level.

## Out of scope for V1.39

- **StarDist integration.** Out of scope; the lab does not use it,
  and dual TF/PyTorch GPU memory contention is its own problem.
- **GPU paths for the recipe enhancement plugins.** Most are
  OpenCV / skimage; adding a `compute.gpu.ops`-style wrapper for
  them is a maintenance tax with no payoff against V1.33's
  profiling baseline.
- **GPU paths for the `nd2`/TIFF decoders.** Decoding stays CPU.
- **Custom CUDA kernels.** `cucim` covers what we need.
- **Pyramid janitor / disk quota.** The user can `rm -r`
  `~/.nd2studios/workspace/sessions/<hash>/pyramid/` manually; an
  automatic janitor is a future polish.
- **Cross-machine pyramid portability.** Pyramids live under
  `~/.nd2studios/workspace`; sharing happens by zipping the
  workspace dir (works) or by re-import on the second machine
  (also works, just rebuilds the pyramid). The hash key matches so
  the second machine will not re-build *if* the workspace dir was
  copied with it.
- **Persisting the GPU/pyramid checkboxes across launches.** Settings
  live in module state for V1.39; a future phase can wire them to
  a `~/.nd2studios/preferences.json`.
- **Materialising `processed.zarr` for the Recipe stage.** Still out
  of scope; the V1.38 reasoning (skimage / OpenCV plugins are
  millisecond-scale per frame) still holds.

## Risk and rollback

The package is additive. Every existing CPU code path keeps working
unchanged. Rollback options, smallest first:

- Set `ND2_DISABLE_GPU_ANALYSIS=1` in the environment —
  `compute.gpu.ops.*` skip the GPU branch even when CuPy is
  available. Reproduces V1.38 analysis behavior exactly.
- Set `ND2_DISABLE_PYRAMIDS=1` — `BuildPyramidJob` is never
  submitted and `MultiAxisViewer._active_level` is pinned to 0.
- Uncheck both Performance dialog checkboxes — same as the two env
  vars but in the GUI.
- Revert the touchpoints in `import_page.py`,
  `multi_axis_viewer.py`, the two analysis backends, and
  `main_window.py`. The `compute/gpu/` and
  `pipeline/stages/pyramid_stage.py` packages become dead code,
  harmless.

No on-disk schema change for `.nd2s`. The workspace gains a
`pyramid/` subdirectory but the existing `manifest.json` schema is
backward-compatible (new key in `stages`; readers that don't know
about it ignore it).

## After this phase

The seven phases give us:

1. **Phase 1 (V1.33)** — profiling baseline.
2. **Phase 2 (V1.34)** — lazy loading + threading.
3. **Phase 3 (V1.35)** — RAM cache + prefetch.
4. **Phase 4 (V1.36)** — pyqtgraph display.
5. **Phase 5 (V1.37)** — background analysis with cancellation.
6. **Phase 6 (V1.38)** — pipeline workspace + stage commits.
7. **Phase 7 (V1.39)** — optional GPU + pyramids.

What is genuinely new in V1.39 versus the generic Phase 7 doc:

- ND2Studios's display GPU path was already in place at V1.36; this
  phase adds an *analysis*-GPU path that is independent of display.
- Pyramid level 0 is *not stored* — the existing
  `LazyND2Volume.get_frame` IS the level-0 reader.
- StarDist and recipe-plugin GPU paths are deliberately out of
  scope; only the actual hot ops (spots scale-space, tear-detection
  filter chain) get GPU dispatch.
- The pyramid stage piggybacks on the V1.38 `Session` for
  cross-launch caching, which the generic Phase 7 doc did not
  assume.

Verify before declaring V1.39 done:

- A complete workflow (Import → Recipe → Export → Analysis →
  Results) runs end-to-end on a representative ND2 file with
  pyramids built and GPU mode enabled.
- The Phase 1 profiling harness shows monotonic improvements (or
  no regressions) on metrics that matter: analysis preview latency,
  slider scrub frame time at high zoom, GPU vs CPU spot-detection
  runtime.
- The application gracefully degrades on each removed capability:
  no CuPy, no `cucim`, no `zarr`, no Cellpose, no pyramid — all
  should just work with a slightly slower but functional UX.
