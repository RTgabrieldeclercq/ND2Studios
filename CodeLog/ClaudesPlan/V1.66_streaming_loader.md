# V1.66 — Streaming / memory-mapped loader (NIS-Elements-style)

**Status:** Implemented (core)
**Author:** Claude (with G. Declercq)
**Problem:** Opening a large file freezes/lags the GUI while the app "materializes
the file into RAM." **Goal:** open instantly and stream on demand, like Nikon
NIS-Elements, without ever holding the whole volume in RAM.

---

## 1. Diagnosis — why it froze

Since V1.41 the loader eagerly builds the **entire** `(M,T,Z,H,W)` array per
channel (`materialized_loader.materialize_nd2` / `materialize_from_volume`:
`np.empty((n_m,n_t,n_z,h,w))` then decode every plane). Consequences:

- **All-or-nothing latency** — `BaseWorker.finished` only fires after 100% of the
  file is decoded, so nothing displays until the whole thing is read.
- **GIL-bound per-plane work on 8 threads** starves the GUI event loop → lag.
- **Peak RAM = full footprint** (+ a projected copy held simultaneously).
- The `LoadStrategy` selector already had a `LAZY_CACHED` mode, but it was
  **only honored for single-file ND2**; TIFF and every multi-file path ignored
  the decision and always materialized. The eager threshold was **50% of RAM**,
  so a big-RAM machine eager-loaded very large files.

### Measured on the real file (`GELS_TFM.tif`, provided by G. Declercq)

56.25 GB uncompressed BigTIFF, `(T=9, Z=100, C=2, Y=4096, X=4096)` uint16,
profiled in a 3.8 GB sandbox:

| Operation | Eager (current) | Streaming (V1.66) |
|---|---|---|
| Open → first pixel | **~5 min, needs 56 GB RAM** (cannot complete < file size) | **~20 ms, ~30 MB RAM** |
| Single-Z frame | (already resident) | 0.17 s cold, then **cached (instant)** |
| Peak RSS | 56 GB anonymous heap (swaps/OOM) | < 1 GB, **reclaimable page-cache** |

Eager simply cannot open this file on a machine with less RAM than the file, and
is a multi-minute freeze even on a 128 GB host.

## 2. How NIS-Elements does it (and what we adopt)

NIS opens a large image by loading only a **thumbnail**, then **streams** pixels
progressively as you zoom/navigate, backed by a **multi-resolution pyramid** for
fast display. We adopt: (a) **memory-map / lazy open** (metadata only), (b)
**stream frames on demand**, (c) **bounded LRU cache + neighbour prefetch** for
smooth scrubbing, (d) reuse the existing **pyramid** (built post-import) for
zoomed-out display. Pixels are never all resident at once.

## 3. `StreamingDataset` — the drop-in replacement

`nd2studios/backend/streaming_dataset.py` (pure numpy, Qt-free). Implements the
**exact** `MaterializedDataset` public surface (`get_frame`, `get_volume`,
`to_lazy_channel`, `all_channels_as_lazy`, `channel_array`, `subset`, `reopen`,
`close`, `shape`, `n_*`, `channel_names`, `pixel_size_um`, `z_step_um`, `dtype`,
`z_mode`) — so the viewer, recipe and export pipelines need **zero changes**.

- **`TiffMemmapSource`** — `tifffile.memmap(mode="r")` for uncompressed/contiguous
  (Big)TIFF (true OS-paged mmap), parsing the series axes (`TZCYX`, …) to slice
  the right Z range; per-page `asarray` fallback for compressed/tiled TIFFs.
- **`LazyVolumeSource`** — wraps any lazy volume exposing `get_volume`
  (`LazyND2Volume` today), so ND2 streams through the same machinery.
- **Bounded LRU frame cache** (byte-capped, thread-safe): a revisited frame is
  instant; resident bytes never exceed the budget (`recommended_cache_budget_bytes`).
- **Neighbour prefetch** — a single background thread (its own `reopen()`'d
  source; handles are not thread-safe) warms `t±1` so scrubbing hides latency.
  Deep projections are **not** prefetched (too large — they rely on the cache
  after first view + the pyramid).
- **Blocked Z-projection** — a max/mean/min projection over a deep stack is read
  in Z-blocks (~256 MB each) and reduced incrementally, so a 100-slice projection
  never allocates the full 3.2 GB stack in heap (matters for the ND2/per-page
  path; identical numerical result — verified).

## 4. Strategy change — streaming is the overarching viewing setup

`utils/resource_strategy.py`:

- **`STREAM_ALWAYS_DEFAULT = True`** (mirrored by `Settings.STREAM_ALWAYS`) —
  `choose_strategy` returns `LAZY_CACHED` for **every** file, so all viewing goes
  through the on-demand `StreamingDataset` (uniformly instant + smooth). The
  hard-cap OOM guard is skipped when streaming (it never materializes). Eager
  full-RAM loading is opt-in via `FORCED_LOAD_STRATEGY = "eager_full"` (honored
  on all four load paths) for a small resident file that wants zero per-frame
  latency. `DISPLAY_PREVIEW_Z_PLANES` defaults to 32 (deep-Z display preview on).

The eager-threshold logic below still governs behaviour when streaming is
disabled:

- New **absolute cap** `EAGER_MAX_BYTES_DEFAULT = 2 GB`: `eager_cap =
  min(fraction × RAM, 2 GB)`. A file larger than the cap **streams** even on a
  big-RAM host (so a huge acquisition opens instantly). Small files still load
  eagerly for zero per-frame latency.
- **Streaming-first fallback** — when the full volume doesn't fit the eager
  budget, choose `LAZY_CACHED` (which **preserves Z** for the V1.65 3-D viewer /
  Z navigation) instead of `EAGER_REDUCED` (which collapsed Z at load).
  `EAGER_REDUCED` remains available via a forced override.

Verified: the 56 GB Z-stack on 128 GB → `lazy_cached`, `z_collapsed=False`; a
~1 GB file → `eager_full`.

## 4.1 Stream-for-view / materialize-for-analysis split

Streaming is ideal for *viewing* (instant, low RAM, cache + prefetch) but adds
per-frame overhead that can slow a *tight analysis loop* over a file that would
comfortably fit in RAM. So the two workloads are split:

- **Viewing** always uses the `StreamingDataset` (`record._raw_volume`).
- **Analysis / compute** goes **resident when it fits**: `fits_resident(volume)`
  (`utils/resource_strategy.py`) is a RAM-relative check (`≤ EAGER_MAX_FRACTION`
  of available, no memory pressure) that *ignores* the small absolute
  `EAGER_MAX_BYTES` view-open cap — so on a big-RAM host a multi-GB stack that
  streams for viewing is still materialized for analysis. It drives:
  - `should_stream_analysis` — a streamed dataset that fits → in-RAM analysis
    (labels in RAM); only one too big to fit streams (labels spill to disk).
  - `materialize_channels_if_fits(channels, volume)` — the analysis page reads
    its lazy input channels into RAM when they fit, else keeps them lazy.
- The recipe path already materializes per-channel (`RecipeWorker`), and memory
  pressure (`MemoryMonitor` CRITICAL+) forces streaming regardless of size.

Net: **view streams; compute materializes when it fits, streams when it doesn't.**

## 5. Loader wiring — honor the decision

`workers/load_worker.py`:

- **`_load_tiff`** (single file) — on `LAZY_CACHED`, open via
  `StreamingDataset.from_tiff(path, …)` (memmap) instead of `materialize_from_volume`.
- **`_load_nd2`** — on `LAZY_CACHED`, wrap `LazyND2Volume` in
  `StreamingDataset.from_volume(...)` (adds the working cache + prefetch that the
  old path lacked — `configure_cache` never existed on `LazyND2Volume`).

`workers/pre_render_worker.py` — the bulk 500-frame RGB pre-render now **skips**
any dataset without an in-RAM `channels` dict (i.e. streaming), so the CPU-canvas
fallback path reads on demand instead of crashing / re-eager-loading.

## 6. Follow-ups

**Done (this pass):**

- **Multi-file ND2/TIFF streaming** — `LazyVolumeSource` now falls back to
  stacking per-plane `get_frame` reads when a volume lacks `get_volume`, so the
  multi-file composites (`LazyMultiFileND2Volume` / `LazyMultiFileTIFFVolume`)
  stream through the same cache. `_load_nd2_multi` and `_load_tiff_multi` honor
  `LAZY_CACHED` via `StreamingDataset.from_volume` (composite kept open for
  on-demand reads; only the eager path closes it).
- **Deep-Z fast display** — `StreamingDataset` gained a bounded **Z-subsampled
  preview** for the display path: `get_frame` can project ≤ `preview_planes`
  evenly-spaced planes (**4.2× faster** on the 100-Z file: 4.0 s vs 16.9 s),
  while `to_lazy_channel` / `get_volume` (recipe / export / DVC) stay **exact**.
  Gated by `Settings.DISPLAY_PREVIEW_Z_PLANES` (**default 0 = exact**,
  correctness-first; set e.g. 32 in the Performance dialog to trade a little
  display fidelity for speed). Preview is an approximation (corr ≈ 0.95 vs exact
  — max can miss a bright pixel in a skipped plane), hence off by default.

**Remaining:**

- **Display pyramid for the initial frame** — wiring the existing V1.39 XY
  pyramid into the *first* display (not just post-Confirm) would give a true
  NIS-style instant thumbnail for a deep max-projection even with preview off.
- **First-frame-before-100%** for the (small-file) eager path.

## 7. Testing & verification

- **`tests/streaming/test_streaming_dataset.py`** — 11 headless cases (cache
  eviction bounds, projection correctness incl. blocked, `to_lazy_channel` proxy,
  `subset`, `reopen`, prefetch no-crash, `LazyVolumeSource`).
- **Real-file profiling** on `GELS_TFM.tif` (numbers in §1): open 20 ms/30 MB,
  cached revisits instant, peak RSS < 1 GB on a 56 GB file.
- **Blocked vs full projection** — byte-identical result, confirmed on the real file.
- Sandbox caveat: this build environment has no OpenGL/PySide6 GL libs, so the
  GUI wasn't executed here; the backend + strategy are validated headlessly and
  on the real file. `tifffile` is already a core dependency (no new requirement).

## 8. Risks

- **Odd TIFF axis metadata** — `from_tiff` trusts `tifffile`'s series axes;
  standard OME/ImageJ/BigTIFF (incl. the provided file) parse correctly. Files
  with ambiguous axes may need the composite metadata path (follow-up).
- **First-touch latency** on an uncached far-jump frame (mitigated by prefetch +
  cache; negligible on NVMe). This is the deliberate streaming trade-off G.
  Declercq approved ("stream on demand").
- **Behavior change**: large Z-stacks that previously loaded `EAGER_REDUCED`
  (Z-collapsed) now stream with Z preserved — aligned with the 3-D viewer, and
  `EAGER_REDUCED` is still reachable via forced override.
