# V1.46 — Pipelines page: node graph is the authoritative Processing recipe

## Problem

On the Pipelines page the **Processing node graph** and the committed
`record.recipe` are two independent sources of truth:

- The **Processing** sub-tab preview linearizes the *graph* (`recipe_for_node`
  from the previewed / output node). An empty graph (Input wired directly to
  Output, or nothing wired) → empty recipe → raw image.
- The **Analysis** sub-tab base image, and every per-frame processed read, use
  `record.recipe` / `record.recipe_normalized` directly
  (`_show_base_image` → `ProcessedFrameVolume`; `_extract_processed_frame` →
  `apply_recipe`). `record._processed_view` (an `EnhancedDataset`) backs
  `processed_view()`.

`record.recipe` is only written by an **explicit Apply**, by the legacy Recipe
page, by config load/save, or by loading a session — **never** by editing the
Pipelines node graph, and building an empty graph never clears it.

Result: a Background Subtract (or any step) committed through one of those
routes stays live on the Analysis tab and in exports even though the user's
Processing graph is empty. Symptom reported: "the processing pipeline runs a
background subtract even though no such nodes are connected to the output node"
— visible only after switching to the Analysis tab.

## Goal (option A — graph authoritative)

Make the Pipelines **Processing node graph** the single source of truth for the
committed recipe. When the user leaves the Processing sub-tab, re-derive
`record.recipe` from the graph's primary output chain and sync the record's
processed-data fields. An empty / disconnected graph therefore **clears** any
stale committed recipe, so the Analysis tab (and exports) show raw.

## Approach

`nd2studios/pages/pipelines_page.py`:

1. `_graph_recipe() -> List` — derive the recipe the Processing graph currently
   represents: linearize the primary OUTPUT node's chain via `recipe_for_node`.
   Returns `[]` when there is no OUTPUT node or the OUTPUT is not connected back
   to the INPUT (`recipe_for_node` raises `ValueError`). A direct Input→Output
   wire also linearizes to `[]` (raw).
2. `_sync_committed_recipe_from_graph()` — mirror the *record-side* of
   `_apply_processing`: set `record.recipe`, `record.recipe_normalized`
   (= `self._normalized`), drop `record._processed_channels`, and rebuild
   `record._processed_view = EnhancedDataset(...)` (or `None` when the recipe is
   empty). Guarded by a no-op check so an unchanged recipe never rebuilds the
   dataset. Does **not** persist to the session workspace — that stays the
   explicit **Apply** action (durable commit + "preprocessed" status).
3. Call `_sync_committed_recipe_from_graph()` at the top of `_select_stage`
   whenever transitioning **away from** Processing (prev is PROCESSING and the
   new stage is not). This runs before the ANALYSIS branch calls
   `_show_base_image`, so the base image reflects the graph immediately.

## Files

- `nd2studios/pages/pipelines_page.py` — add `_graph_recipe` +
  `_sync_committed_recipe_from_graph`; call the sync on leaving Processing in
  `_select_stage`.

## Key decisions

- **Graph wins.** A recipe committed via the legacy Recipe page / config load /
  session that is *not* represented in the Pipelines graph will be overridden
  (typically cleared) once the user leaves the Pipelines Processing tab. This is
  the intended semantics of option A and the fix for the reported bug.
  Populating the graph *from* a loaded recipe (option B) is a separate feature.
- **Apply unchanged.** Explicit Apply still performs the durable commit
  (session-workspace persist + status). The auto-sync only keeps the in-memory
  record consistent with the graph for the Analysis/Results previews.
- **Cheap.** `EnhancedDataset` is lazy, and the no-op guard means the sync only
  rebuilds it when the effective recipe actually changed.
