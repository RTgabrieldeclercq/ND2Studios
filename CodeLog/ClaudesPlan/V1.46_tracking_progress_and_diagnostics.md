# V1.46 — Track Objects: progress plumbing, diagnostics, safe speedups

## Symptom

After a successful StarDist segmentation, the **Track Objects** node
(method = *Cell-Tracker: Topology (Hungarian)*) is very slow and shows **no
progress** — the bar sits at 0 % until it finally jumps to done. The fix must
generalize to the other methods (centroid, SerialTrack, Cell-Tracker fingerprint).

## Root-cause diagnosis (read before touching code)

**No progress.** `_TrackJob.run` (`pages/pipelines_page.py`) reports `0.0` then
`1.0` around a single blocking `link_objects_with_params(...)` call. The vendored
`track_timeseries` *accepts* a `progress_cb`, but it is never threaded through
`link_objects_with_params → link_objects → _link_group_celltracker →
track_timeseries`. So tracking is completely opaque and also **uncancellable**
mid-run.

**Slowness (CT topology on a dense field), in decreasing safety-of-fix order:**
1. `df.apply(lambda row: track_ids.get((frame, label)), axis=1)` for the final
   `track_id` column — a Python call + Series construction per row. At 100k+
   detections this alone is tens of seconds. `track_fingerprint` has the same.
2. Repeated `df[df["frame"] == f]` boolean masks *inside* the per-frame loop —
   each rescans the whole frame → O(T²·cells).
3. `compute_topology_features` runs a Python `for i in range(N)` loop per frame
   (twice: prev + curr).
4. `linear_sum_assignment` on the full N×M cost matrix per frame — O(n³),
   **inherent** to a global-assignment tracker. On thousands of nuclei this
   dominates and cannot be changed without altering the tracking result.

## Approach

### 1. Diagnostics (the "double-check what's going on")
Add a module logger to `celltracker/tracking.py` and `object_tracker.py`:
- On entry: detection count, frame count, mean detections/frame, method.
- Time the link loop, the topology-feature computation, and the final
  `track_id` assignment **separately**, logged at the end.
- Warn when the largest per-frame cost matrix is big (e.g. `N*M > 4e6`),
  naming the O(n³) Hungarian as the inherent cost so a dense-field slowdown is
  explained rather than mysterious.

### 2. Progress plumbing (the general fix — works on every method)
Thread a backend-pure `progress_cb: Callable[[float, str], None]` (fraction
0–1 + message) from `_TrackJob` down through `link_objects_with_params →
link_objects → _link_group_*`. `link_objects` splits the 0–1 range across its
`(channel, m_position)` groups; each linker reports per-frame within its slice.
`track_timeseries` / `track_fingerprint` switch their `progress_cb` to the same
`(fraction, message)` convention (only our bridge calls them). `_TrackJob`'s
callback also polls `self.token`, so a long track is now **cancellable**.

### 3. Safe, result-identical speedups
- Vectorize the final assignment: replace `df.apply(axis=1)` with a list-comp
  over `zip(frame_arr, label_arr)` + `track_ids.get(...)`.
- Group once: `df.groupby("frame")` into a dict instead of repeated masks.
- Vectorize `compute_topology_features` (K is uniform across cells, so the
  per-cell loop becomes array ops; keep the `k > 1` guard so k==1 stays zeros —
  bit-for-bit equivalent to the loop).

Item 4 (Hungarian) is **left as-is** — changing it changes results. Diagnostics
make its cost visible; a future item could add distance-gated sparse assignment.

## Files
- `nd2studios/backend/celltracker/tracking.py` — logger + timing; vectorized
  features + assignment + groupby; new `progress_cb(frac, msg)` convention.
- `nd2studios/backend/object_tracker.py` — thread `progress_cb` through
  `link_objects` / `link_objects_with_params` / all four `_link_group_*`.
- `nd2studios/pages/pipelines_page.py` — `_TrackJob` passes a token-polling
  progress callback.
- `tests/test_tracking_topology.py` — new: proves vectorized
  `compute_topology_features` matches the original loop, and that
  `track_timeseries` still assigns sensible ids; asserts progress is reported.

## Verification

- Unit test: `track_timeseries` / `track_fingerprint` emit monotonic progress

- Manual: run Track Objects on a StarDist result; bar advances per frame; the
  log shows counts + per-stage timing.
