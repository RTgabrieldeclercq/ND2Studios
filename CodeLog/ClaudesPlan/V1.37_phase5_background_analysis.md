# V1.37 — Phase 5: Background Analysis with Cancellation

## Goal

Make every analysis operation **non-blocking, cancellable, and tiered
into Preview vs Commit**, with a single coordinated job runner that
coalesces redundant submissions and shuts down cleanly on app exit.
After this phase, dragging a parameter slider on the Analysis page
updates the on-screen overlay at interactive speed for the current
(M, T) frame, and "Run Analysis" still streams the full-stack work to
the background — but both routes go through the same plumbing,
cancellation is real, and stale previews never overwrite a fresh
one.

## Where ND2Studios already stands

The Phase 5 doc was written for a generic app where analysis still
blocks the GUI. ND2Studios is further along than that baseline:

- `AnalysisWorker(BaseWorker(QThread))`
  ([nd2studios/workers/analysis_worker.py](nd2studios/workers/analysis_worker.py))
  already runs `AnalysisPipeline.run()` off the GUI thread, with a
  `cancel()` flag forwarded through `cancelled_cb` and progress /
  status / finished / error signals on `BaseWorker`.
- `AnalysisPage`
  ([nd2studios/pages/analysis_page.py](nd2studios/pages/analysis_page.py))
  already has two tiers: **Run Analysis** (commit, sequential per-M) and
  **Screen frame / Auto-screen** (preview on the currently visible
  (M, T)). Auto-screen even debounces 300 ms after a viewer-coords
  change.
- `RecipeWorker`
  ([nd2studios/workers/recipe_worker.py](nd2studios/workers/recipe_worker.py))
  is the Recipe page's equivalent — its Trial / Accept / Reject flow
  is structurally similar but tied to enhancement plugins and recipe
  state, not the AnalysisPipeline registry.
- `BaseWorker`
  ([nd2studios/workers/base_worker.py](nd2studios/workers/base_worker.py))
  keeps a class-level registry of running threads so the GC can't
  destroy a `QThread` while its OS thread is still alive — a known
  PySide6 footgun.
- `recommended_worker_count()`
  ([nd2studios/utils/resources.py](nd2studios/utils/resources.py))
  is in place and the docstring already calls out Phase 5 will pick
  it up.

So the Phase 5 doc's abstract-base-class architecture is a fit —
just not as a wholesale replacement. The aim is to **add a thin
coordination layer on top** of what's there, not throw away
`BaseWorker` or `AnalysisWorker`. The new layer earns its keep by
giving us four things the current code can't:

1. **Parameter-change-driven previews.** Today, dragging a threshold
   slider on the Analysis page does *not* trigger a re-screen — only
   moving the T/M/Z slider does (`_on_viewer_coords_changed` →
   debounce → `_screen_current_frame`). Researchers tweaking a
   Hysteresis or Otsu cutoff have to keep nudging the viewer slider
   between every parameter tweak. The new runner makes
   `params_changed` a first-class trigger, with the same 80–300 ms
   debounce.
2. **Key-based job coalescing.** Each submission carries a key
   (e.g. `"analysis_preview"`); a second submission with the same
   key while the first is in flight cancels the first. Today,
   `_screen_current_frame` *does* cancel `self._screen_worker`
   before launching a new one, but that logic is hand-rolled on
   each page; the new runner centralizes it.
3. **A real cancellation token.** `BaseWorker._cancelled` is a bool
   flag with no thread-safe semantics. We move to a
   `threading.Event`-backed `CancellationToken` whose `.check()`
   raises `CancelledError` from inside the worker. Existing
   `cancelled_cb` callers keep working — `CancellationToken` exposes
   an `is_cancelled()` shape compatible with the current callback.
4. **Coordinated app-exit shutdown.** On window close, every page
   that owns workers needs to drain them. Today this is implicit
   (Python GC + `BaseWorker._running`). The runner owns the set of
   active jobs explicitly and `MainWindow.closeEvent` can wait on
   them.

## Architecture

```
nd2studios/compute/
├── __init__.py
├── cancellation.py       # CancellationToken, CancelledError
├── progress.py           # ProgressReporter (QObject with signals)
├── jobs.py               # AnalysisJob ABC, JobResult dataclass
├── runner.py             # JobRunner (QThreadPool wrapper, coalescing)
├── result_store.py       # In-memory result cache, keyed by job key
└── pipeline_jobs.py      # AnalysisPipeline → AnalysisJob adapters
                          # (PipelinePreviewJob, PipelineCommitJob)
```

The runner is held on `MainWindow.job_runner` and passed down to
pages that opt in (the Analysis page in this version). It is a
project-wide singleton-by-convention, not a hard singleton — the
Batch page already runs many `BatchWorker`s in parallel and is not
moved onto the runner in V1.37 (out of scope; the batch path
already has its own concurrency design).

### `CancellationToken` (`cancellation.py`)

A `threading.Event` wrapper. Three methods:

- `cancel()` — sets the event.
- `is_cancelled() -> bool` — non-raising check. Matches the
  signature `AnalysisPipeline.run(..., cancelled_cb=lambda: ...)`
  expects, so existing pipelines can take a `token.is_cancelled`
  bound method as their `cancelled_cb` with no edits.
- `check()` — raises `CancelledError` if set. New code uses this
  inside loops where we want cooperative cancellation.

### `ProgressReporter` (`progress.py`)

A tiny `QObject` with one signal `progress(str, float, str)` —
`(job_key, fraction_0_to_1, message)`. The runner instantiates one
per job and gives the job a callable shim
`progress(fraction, message="")` that emits on its behalf. The
shim is the type the existing `AnalysisPipeline.run(progress_cb=…)`
takes (int 0–100); we expose both forms so pipelines don't change.

### `AnalysisJob` (`jobs.py`)

ABC with:

- `key: str` — coalescing key.
- `token: CancellationToken`.
- `run(progress) -> Any` — implementer.
- `cancel()` — delegates to the token.

`JobResult` is a frozen dataclass `(key, ok, value, error)`.

### `JobRunner` (`runner.py`)

QObject with:

- An internal `QThreadPool` sized by
  `recommended_worker_count()`.
- A `dict[str, AnalysisJob]` of active jobs, protected by an
  `RLock`. On `submit(job)`, any existing job under the same key is
  cancelled before the new one runs.
- Signals: `job_done(JobResult)`, `job_cancelled(str)`,
  `job_progress(str, float, str)`.
- `cancel(key)`, `cancel_all()`, `shutdown(wait_ms=5000)`.

The runner uses a `QRunnable` wrapper (not a `QThread` subclass) so
the pool can fan out CPU-bound work across cores without us
managing thread lifecycle. This is the *only* place in ND2Studios
that uses `QThreadPool`; everything else stays on `QThread` /
`BaseWorker`. The mix is intentional — `QThread` is right for the
long-running, signal-heavy `RecipeWorker` / `BatchWorker` /
`AnalysisWorker(commit)` / `IOWorker` cases; `QThreadPool` is right
for the short, fire-and-forget preview path.

### `ResultStore` (`result_store.py`)

A keyed in-memory cache for job outputs, with an `RLock`. The
Analysis page uses it to remember the most recent preview result
across param changes, and to short-circuit redundant work.

### Pipeline adapters (`pipeline_jobs.py`)

Two `AnalysisJob` subclasses bridge to the existing
`AnalysisPipeline` registry without touching the pipelines
themselves:

- **`PipelinePreviewJob`** — runs an `AnalysisPipeline` on a
  *single* `(M, T)` frame and returns the resulting
  `AnalysisResult`. The job receives the pipeline class, the
  selected channel name, a `(1, H, W)` frame array (already
  extracted from the volume on the GUI thread — cheap on a cache
  hit), the metadata dict, and the params dict. The pipeline's
  existing `run(channels, metadata, params, progress_cb,
  cancelled_cb)` signature is used as-is; we pass `token.is_cancelled`
  as `cancelled_cb` and a `progress_cb` that forwards 0–100 ints
  into `progress.update(fraction)`.
- **`PipelineCommitJob`** — runs the pipeline on full channel
  arrays for a single M position. The Analysis page currently
  iterates M positions sequentially in its own state machine
  (`_run_queue`, `_start_next_m_run`, `_on_finished`), and *that
  state machine is preserved*. The commit job replaces one
  `AnalysisWorker` invocation per M.

Both jobs check `self.token` at sensible cadences and raise
`CancelledError` for fast unwinding when the user clicks Cancel.

The `AnalysisWorker(BaseWorker)` class is **kept** for now —
nothing else needs to change to ship V1.37, and removing it would
turn into an "audit every QThread reference" exercise. We mark it
deprecated in its docstring and leave the migration to a later
version.

## Wiring into `AnalysisPage`

The page builds a `JobRunner` reference from its `main_window`
parent (`main_window.job_runner`). Three wiring changes:

1. **Param-change driven preview.** Connect
   `self.param_editor.params_changed` →
   `_on_params_changed_for_preview`, which restarts the
   `_screen_debounce` timer just like the existing
   `_on_viewer_coords_changed` does. The debounce timer's slot
   stays the same — it calls a *new* `_submit_preview_job` that
   replaces the body of `_screen_current_frame`.
2. **Replace `_screen_current_frame`'s manual worker plumbing with
   a runner submission.** The new body extracts the single frame
   (already does), then constructs a `PipelinePreviewJob` with key
   `"analysis_preview"` and submits it. `_on_screen_finished` is
   replaced by a `_on_runner_done` slot that filters on
   `result.key` and routes preview / commit results.
3. **Replace each `AnalysisWorker.start()` in the multi-M run
   queue with a `PipelineCommitJob.submit(...)`.** The state
   machine (`_run_queue`, `_current_run_m`, `_run_total`) is
   unchanged — only the worker class changes. Per-M progress is
   delivered through `job_progress`.

Auto-screen continues to also fire on viewer-coord changes. Both
triggers feed the same debounce timer; the timer firing submits a
preview job with the same key, so a rapid sequence "slider →
slider → param" results in exactly one preview job in flight (the
runner cancels the previous on submit; the debounce reduces
churn).

The legacy `Cancel` button now calls
`runner.cancel("analysis_commit")` and clears the run queue. The
existing per-frame `cancel()` short-circuit in the manual-mask
pipeline still works because the cancellation token is wired
through `cancelled_cb`.

## App-exit cleanup

`MainWindow.closeEvent` is currently absent — the default close
path lets Python GC handle workers, leaning on
`BaseWorker._running` to keep refs alive. We add a `closeEvent`
that:

1. Calls `self.job_runner.shutdown(wait_ms=5000)`.
2. For each page with `on_close()` method, calls it (only one page
   defines it for now — the Analysis page drops its debounce
   timer and waits on the legacy `_worker` / `_screen_worker` if
   any are mid-flight).

`MainWindow.__init__` is also where `self.job_runner = JobRunner()`
is instantiated, before any page is built.

## Acceptance criteria

- [ ] Dragging a parameter slider on the Analysis page (e.g.
  `p_low` on Histogram Threshold, `min_sigma` on Spots) updates
  the on-screen overlay within ~80–300 ms (debounced) of the
  drag release, without blocking the GUI.
- [ ] Rapid slider movement does *not* produce a queue of stale
  preview jobs — at most one preview is in flight at any time
  (verified by logging job submissions).
- [ ] "Run Analysis" launches a commit job; the GUI remains
  responsive throughout (the progress bar advances, the rest of
  the UI is interactive).
- [ ] Clicking Cancel stops the commit job within ~1 second.
- [ ] Closing the app while a preview *or* commit is mid-flight
  no longer prints "QThread: Destroyed while thread is still
  running" — the runner's `shutdown()` drains and waits.
- [ ] Manual Mask, Histogram Threshold, Nuclei, Tear, and Spots
  pipelines all work via the new preview path with no edits to
  their `.run()` implementations.
- [ ] Existing session save/load (`.nd2s`) is unchanged — no
  format migration.
- [ ] `AnalysisWorker` is still importable; nothing outside
  `analysis_page.py` had to be touched.

## Out of scope for V1.37

- **Refactoring `RecipeWorker` / `BatchWorker` / `LoadWorker` /
  `PrefetchWorker` / `StitchWorker` / `IOWorker` onto the new
  runner.** Each is a long-running, signal-heavy QThread today;
  the runner's `QThreadPool` model fits short jobs better. A
  later phase can revisit.
- **Removing `BaseWorker` / `AnalysisWorker`.** Deprecated in
  docstring only. Removing them would force changes in unrelated
  pages.
- **Numba / Dask / dask-image acceleration.** The Phase 5 doc
  mentions these as optional installs; ND2Studios pipelines
  already use scikit-image / scipy / OpenCV with the GIL released,
  and benchmarks have not shown CPU bound-ness to be the issue.
  Defer to a profiling-driven decision.
- **A `tests/perf/` job-runner smoke test.** Worth adding once
  the runner is settled; for V1.37 the acceptance criteria are
  verified manually.

## Risk and rollback

The runner is additive. The legacy paths (`AnalysisWorker`,
manual `_screen_worker`) remain importable; the only behavior
change is that the Analysis page routes through the runner.
Rollback options, smallest first:

- Revert `analysis_page.py` to its pre-V1.37 worker plumbing.
  The `compute/` module is unused and harmless.
- Or revert the whole commit. No on-disk format changes.

No `.nd2s` schema migration; no recipe format change; no
external-dependency bump. `psutil` is already pinned (Phase 2);
no new requirements.

## After this phase

Phase 6 (pipeline tabs with Zarr handoff) will use the runner to
spawn long pipeline-bounded jobs that stream their output to
Zarr instead of holding intermediate stacks in RAM. The
`ResultStore` becomes the in-RAM staging area in front of the
Zarr write — V1.37 ships it empty in spirit, but with the right
shape so Phase 6 doesn't have to redesign it.
