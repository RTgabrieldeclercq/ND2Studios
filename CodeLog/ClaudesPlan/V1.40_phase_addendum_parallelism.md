# V1.40 — Phase Addendum: Multi-Core Parallelism

Applies `CodeLog/ClaudesPlan/08_addendum_parallelism.md` to ND2Studios's
V1.34 / V1.38 / V1.39 codebase. The original 7-phase plan delivered the
profiling baseline, the lazy I/O worker, the prefetch cache, the
pyqtgraph display, the cancellable job runner, the Zarr session
workspace, and the optional GPU + pyramid tiers. It left clear
parallelism gaps in the analysis pipelines, the recipe materialization
path, and most importantly the pyramid build's M×T×Z×C nest.

This document records the choices made when porting the addendum to
ND2Studios — which patterns applied directly, which were translated,
and which were dropped because their preconditions don't hold here.

## Goal

Close the parallelism gaps without changing user-facing behavior or
adding new third-party dependencies. After this work:

- Pyramid building on a 4+ core machine completes ≈ N× faster than the
  V1.39 sequential implementation (one volume read + downscale + zarr
  write per worker thread, all on GIL-releasing C extensions).
- Tear-detection analysis on a representative timeseries runs ≈ N×
  faster on multi-core hosts; single-frame previews are unaffected
  (only T > 1 benefits from the parallel path).
- Recipe materialization across multiple channels runs ≈ min(channels,
  cores)× faster after a session re-attach (when
  `ND2StudiosRecord._processed_channels` has been released).
- NVMe-class storage is detected at runtime and `IOWorker` can grow to
  two readers sharing one priority queue when the user opens a file on
  a fast disk; spinning disks and SATA SSDs keep the V1.34 single
  reader.

## Approach

### What the addendum prescribes that *applies*

- **Pattern 1 — `ThreadPoolExecutor` for batch C-extension work.**
  ND2Studios's analysis pipelines (tear detection, histogram
  thresholding, spot detection, manual mask) all sit on scipy /
  scikit-image / numpy. Their hot kernels release the GIL, so threads
  scale near-linearly with cores. This is the primary primitive
  applied here.
- **Pattern 2 — `ProcessPoolExecutor` + `shared_memory`** for pure-
  Python CPU-bound work. ND2Studios doesn't have a hot path that fits
  this today (every per-pixel loop already drops into a C extension),
  but the utility is included as a future-proof helper since it's
  cheap to maintain and the addendum's worked example is
  immediately reusable.
- **Pattern 5 — Qt-aware parallel job.** The pyramid build already
  runs inside a `BuildPyramidJob` on the V1.37 `JobRunner`. The outer
  `QRunnable` stays one job; the inner work fans out across a nested
  `ThreadPoolExecutor`. Cancellation propagates through a
  `threading.Event` polled inside the worker.

### What the addendum prescribes that *does not apply*

- **Pattern 3 — Dask threaded scheduler.** ND2Studios does not depend
  on Dask. The lazy file-IO layer uses an in-house `LazyND2Volume`
  proxy, not a Dask array. Adopting Dask just to parallelize a single
  loop would be a multi-MB dependency with its own learning curve for
  a single-PI lab. The equivalent `ThreadPoolExecutor` pattern
  achieves the same scaling on the workloads that matter.
- **Pattern 4 — Numba `@njit(parallel=True, nogil=True)` kernels.**
  ND2Studios's custom hot loops are all expressible in scipy /
  scikit-image — no fall-back-to-Python inner loops survive in the
  current codebase. Numba would also add a 30-60 MB compile-cache
  footprint and a first-call JIT pause the addendum itself flags as a
  pitfall. Skipped on cost-benefit grounds.
- **Free-threaded Python 3.13t.** Forward-looking only; the addendum
  says "ship on regular 3.11+ and revisit when 3.13t leaves
  experimental." We do exactly that — no behavior change needed under
  3.13t because all parallel primitives used here already drop into
  GIL-releasing C extensions.
- **NUMA pinning.** The addendum says "do not pre-optimize." We don't.

### Per-phase work

**Phase 2 — NVMe-aware multi-reader I/O.** Adds `utils/storage.py`
with `is_fast_storage(path)` (Linux sysfs lookup, conservative
fallback on other platforms) and `recommended_io_thread_count(path)`
(returns 2 for NVMe, 1 otherwise). Extends
`utils/threading.py:IOWorker` with an optional `shared_queue`
constructor parameter; adds `WorkerGroup` and `start_io_workers(n)`
helpers. The default `start_io_worker` is unchanged; callers opt into
multi-reader by switching to `start_io_workers`.

**Phase 5 — Parallel analysis + cross-cutting helpers.** Creates a
new `nd2studios/compute/parallel/` subpackage:

- `shared_array.py` — `shared_ndarray` context manager and
  `attach_shared` worker-side reconstructor.
- `process_map.py` — `process_map_planes` driver for pure-Python CPU
  work.
- `thread_map.py` — `thread_map_planes` driver for C-extension work
  (the most common shape).

Then rewrites `TearDetectionPipeline.run`'s per-T loop using a direct
`ThreadPoolExecutor` (the lambda-friendly path, since each task needs
both `volume[t]` and the optional `cs_volume[t]`). Per-frame outputs
are collected and stitched in T-order at the end so the
`label_stack` and `measurements` shapes are byte-equivalent to the
V1.19 sequential layout.

**Phase 6 — Parallel recipe materialization.** ND2Studios deliberately
does not materialize a `processed.zarr` (the V1.38 plan accepted that
trade-off; recipe plugins are fast enough that disk I/O would
dominate). The Phase 6 addendum still applies to
`EnhancedDataset.materialize_all`, which after V1.38's
release-and-rematerialize hook walks every channel sequentially.
Channels are independent, so `materialize_all` now fans out over a
`ThreadPoolExecutor` capped at `min(channels, n_workers)`.
`materialize_channel` gains a `threading.Lock` around the
read-then-write cache update so concurrent callers on the same
channel don't both compute. `clear_cache` is held under the same
lock.

**Phase 7 — Parallel pyramid build.** The biggest concrete win.
`PyramidStage.build`'s nested `for m for t for z for c` loop is
converted to a per-level `ThreadPoolExecutor`. Each worker thread
holds its own `volume.reopen()` handle (registered in a lock-guarded
list so the build's `finally` can close them deterministically — the
executor recycles worker threads and offers no per-thread finalizer).
Zarr writes go to unique `(m, t, z, c)` chunks in a DirectoryStore,
so concurrent writes don't contend. Progress is reported through a
new `_AtomicCounter` so the bar stays monotonic across the worker
threads. Cancellation runs through a `threading.Event` polled inside
the task body; in-flight planes finish, the rest are abandoned, and
the partial Zarr is left on disk for the next build to overwrite.

## Key decisions

1. **Thread-pool over Dask.** Already covered above. The decision is
   "no new dependencies" and the workloads release the GIL, so the
   stdlib path is enough.
2. **Per-thread `volume.reopen()` in the pyramid build.** The `nd2`
   SDK isn't thread-safe across file handles. The V1.34 `IOWorker`
   already established the pattern of one reopen per worker thread;
   the pyramid build adopts the same shape.
3. **Numba and GPU off-limits for the addendum.** GPU dispatch is
   handled by V1.39's `nd2studios.compute.gpu`. Numba is not used.
   The addendum's "throw cores at the loop" goal is met with threads
   alone.
4. **Tear detection only, not all pipelines.** Tear detection has
   the highest per-frame cost (uniform_filter + generic_filter +
   rank_entropy + regionprops). Other pipelines either (a) sit
   inside Cellpose which owns its own CUDA/thread management
   (`nuclei_segmentation.py`), or (b) run cheaply enough that
   parallel-loop overhead dominates. Adding parallel paths to those
   pipelines is deferred until profiling shows a need.
5. **Atomic counter for progress.** Bare `done += 1` is not atomic in
   CPython once the GIL is released inside the worker's C-extension
   call. The `_AtomicCounter` is a 10-line helper kept in
   `pyramid_stage.py`; if a second user appears it migrates to
   `utils/`.

## Verification

The addendum lists three verification approaches. We rely on:

- **Smoke-import checks.** Every changed file is parsed and imported
  in this work to catch the obvious regressions (`import nd2studios.compute.parallel`,
  `from nd2studios.pipeline.stages.pyramid_stage import _AtomicCounter`).
- **Manual wall-time comparison.** The V1.33 profiling harness in
  `profiling/` provides the timing infrastructure. The user runs the
  before/after on a representative ND2 (the McGhee Lab's standard
  4096² × 100T mouse-kidney stack is the reference) and records the
  numbers under `profiling/baselines/phase_addendum.json`.
- **CPU utilisation eye-check.** Task Manager / `htop` shows multiple
  cores active during the parallel paths; Phase 7 pyramid building is
  the easiest to see at a glance because it runs for tens of seconds
  on the reference file.

## Out of scope

- Numba kernels (no current Python hot loop to convert).
- Dask DataFrame for results tables (pandas hot paths are not a
  current bottleneck; the V1.22 Results page reads measurements in
  one shot).
- Multi-process compute for the analysis pipelines (every hot kernel
  already releases the GIL; threads are strictly better).
- Auto-detecting NVMe on Windows / macOS (the V1.34 single-reader
  default already runs fine; the heuristic is opt-in).
