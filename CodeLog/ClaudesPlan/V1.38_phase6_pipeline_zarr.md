# V1.38 — Phase 6: Pipeline Workspace with Per-Source Stage Commits

## Goal

Stop holding every stage of a session in RAM at once. After this phase,
once the user **accepts a recipe** the processed channels can drop out of
memory and be lazily reapplied from the (committed) recipe on demand; once
the user **commits an analysis run** the label masks are persisted to a
per-source workspace and can be released from RAM and re-read on demand.
The user's existing `.nd2s` save flow is untouched — the new artifacts
live in an auto-managed workspace next to the cache, keyed by source
file, so re-opening the same ND2/TIFF later resumes prior committed
stages without rerunning anything.

## Where ND2Studios already stands

The generic Phase 6 doc (`06_phase_pipeline_zarr.md`) assumes a tab-based
app whose tabs map 1:1 to a strict pipeline (`raw → processed → analysis →
results`). ND2Studios is shaped differently:

- **Pages, not tabs.** Navigation is a `QStackedWidget` driven by sidebar
  buttons (`Import → Recipe → Export → Analysis → Results → Batch`), and
  the user can move *backwards*. `Recipe` is the "processed" stage,
  `Analysis` is the "analysis" stage, but `Export` and `Results` are
  parallel downstream sinks of those, not strictly later stages. The
  "moving on is permanent" assumption from the generic doc does *not*
  hold — a researcher commonly returns to Recipe after seeing analysis
  results to tweak a parameter.
- **`.nd2s` already exists.** `ND2StudiosManager` already serializes the
  active session to a JSON manifest + companion NPZ via `save_session()`
  / `load_session()`. We do **not** introduce a competing manifest;
  the Phase 6 workspace is *automatic*, lives at
  `~/.nd2studios/workspace/sessions/<hash>/`, and only carries stage
  artifacts. `.nd2s` keeps its current role as the user-saved session
  bundle.
- **Recipes are parameter-only.** A recipe is
  `List[(plugin_name, params_dict)]` plus a `recipe_normalized` flag.
  This is already small and JSON-serializable. We do **not** need to
  write a materialized processed stack to disk by default — lazily
  reapplying the recipe on cache miss is enough, and matches the
  intent of the generic Phase 6 "parameter-only stages" branch.
- **Analysis results are bulky.** `AnalysisResult.label_masks` is
  `Dict[channel_name, (T, H, W) int32]`; on a 200-frame 2048² file with
  3 channels that's ~5 GiB. *This* is the artifact that genuinely
  belongs on disk and that we want to be able to drop from RAM and
  rehydrate per-page. The Results page reads label masks back to
  compute measurements, and the Export page can write them to TIFF —
  both routes can be served from a backing store.
- **Phase 5 plumbing is already in place.** `compute/JobRunner`,
  `CancellationToken`, `PipelineCommitJob`, and `ResultStore` exist;
  Phase 5 explicitly anticipated Phase 6 sitting a backing store in
  front of `ResultStore`.

The takeaway: Phase 6 for ND2Studios is **lean**. It adds a workspace
keyed by source-file hash, a `Session` that owns it, two `PipelineStage`
adapters (recipe + analysis), and wires them into existing commit points
(`RecipePage._on_accept` and `AnalysisPage._on_finished`). No `.nd2s`
schema migration, no `QTabWidget` rewiring (we don't use one), no GUI
flow change visible to the user beyond a small "Workspace" status line.

## Architecture

```
nd2studios/pipeline/
├── __init__.py
├── session.py         # Session, SessionManifest, StageRecord, hash helpers
├── stage.py           # PipelineStage ABC
├── storage.py         # zarr/npz write helpers with graceful fallback
└── stages/
    ├── __init__.py
    ├── recipe_stage.py    # commits the recipe + provides EnhancedDataset
    └── analysis_stage.py  # commits label_masks + rehydrates on demand
```

### Why a separate `pipeline/` package

`backend/` is required to be Qt-free and data-shape-pure. `core/` already
owns app-level state (`ND2StudiosManager`). `compute/` owns short
cancellable jobs. The new package sits between them: it owns the
**on-disk artifacts** that the rest of the app reads and writes. It
imports from `backend/` (`LazyND2Channel`, `recipes`), is itself Qt-free
(stages signal completion via plain callables), and is read by `pages/`
and `workers/`.

### Session — `session.py`

`Session` owns one workspace directory per source file. The directory is
chosen by hashing `source_path` + size + mtime + the first/last MiB of
content. That last bit is what catches the case "user copied an ND2 to a
new path" — the hash matches, the workspace is reused.

```
~/.nd2studios/workspace/sessions/<source_hash>/
├── manifest.json            # SessionManifest (JSON-only, human-readable)
├── recipe/
│   └── recipe.json          # the committed recipe (List[(name, params)])
└── analysis/
    └── <pipeline_name>/
        ├── m_00/
        │   ├── labels_<channel>.zarr       # if zarr is installed
        │   └── labels_<channel>.npz        # fallback
        ├── m_01/...
        └── summary.json     # per-pipeline summary + provenance
```

The path layout is intentionally regular and human-inspectable. The user
can `rm -r` an `analysis/<pipeline>` subtree to invalidate just that
output, or `rm -r sessions/<hash>` to start fresh for a file.

`SessionManifest` is the same shape as the generic Phase 6 doc but
collapsed to what ND2Studios actually has:

```python
@dataclass
class StageRecord:
    name: str                       # "recipe" | "analysis:<pipeline_name>"
    committed_at: str | None = None # ISO-8601 UTC
    parameters: dict = field(default_factory=dict)
    artifacts: dict[str, str] = field(default_factory=dict)
    # logical name -> relative path inside session dir

@dataclass
class SessionManifest:
    session_id: str
    source_path: str
    source_hash: str
    created_at: str
    n_t: int
    n_m: int
    n_z: int
    n_channels: int
    height: int
    width: int
    pixel_size_um: float
    channel_names: list[str]
    stages: dict[str, StageRecord] = field(default_factory=dict)
```

The hash function is the Phase 6 doc's recipe verbatim (first MiB + last
MiB + size + mtime, sha-256 first 16 chars), which is fast enough that we
can hash on every Import confirmation without a perceptible delay.

### `PipelineStage` ABC — `stage.py`

A trimmed version of the generic doc's ABC. We drop `QObject` and Qt
signals — stages are pure Python and the GUI is notified via the
existing `JobRunner.job_done` path. The base class declares:

- `name: str`
- `commit(self) -> StageRecord`
- `is_committed(self) -> bool`
- `release_in_memory(self) -> None`
- `rehydrate(self) -> None`

Stages never own QThreads or QTimers. Stage `commit()` is called from the
GUI thread (after a worker has already done the heavy lifting); the I/O
in `commit()` is small (JSON manifest + maybe a Zarr or NPZ write).

### `RecipeStage` — `stages/recipe_stage.py`

The processed stage. Its job is parameter-only: persist
`(recipe, recipe_normalized, channel_names)` to `recipe/recipe.json`,
record artifact paths in the manifest, and expose an `EnhancedDataset`
proxy that applies the recipe lazily on demand (one channel-frame at a
time, via the existing `EnhancementPlugin.execute()` API).

```python
class EnhancedDataset:
    """Wraps raw channels; applies a recipe lazily per frame."""
    def __init__(self, raw_channels, recipe, normalized, pixel_size_um):
        self._raw = raw_channels
        self._recipe = recipe
        self._normalized = normalized
        self.pixel_size_um = pixel_size_um

    def get_frame(self, channel: str, t: int) -> np.ndarray: ...
    def materialize_channel(self, channel: str, progress_cb=None) -> np.ndarray: ...
```

`EnhancedDataset` exists so the Export and Analysis pages can keep
working when `_processed_channels` has been released — they call
`materialize_channel()` only at the moment they actually need a full
stack. Today they read `exp._processed_channels[name]`; the new code
path is `exp.processed_view().materialize_channel(name)` and falls
through to the in-memory dict when present.

**This phase does *not* materialize a `processed.zarr`** by default. The
generic Phase 6 doc treats materialization as an option for users who
"export many derivatives." ND2Studios users do export derivatives, but
the recipe is cheap to re-apply (every enhancement plugin is a few-ms
per-frame skimage/OpenCV call); the disk and write-time costs are not
worth it. A `materialize=True` opt-in is left for a later version when
profiling shows a real need.

### `AnalysisStage` — `stages/analysis_stage.py`

The analysis stage. Per `(pipeline_name, m_position)`, commits:

- `labels_<channel>.zarr` (chunked `(T, H, W)` int32, Blosc/zstd-3) if
  the `zarr` package imports successfully.
- `labels_<channel>.npz` (single-array NPZ, uncompressed for speed) as
  the fallback when `zarr` is absent. NPZ is already in the project's
  dependency surface (used by `ND2StudiosManager.save_session`).
- A small `summary.json` per pipeline with `summary` dict + measurements
  count + overlay color/alpha defaults.

`measurements` arrays from the existing `AnalysisResult` are JSON-safe
and small (one dict per region), so they go straight into `summary.json`.
`volumetric_voxel_counts` (Manual Mask only) is also JSON-friendly
once we stringify the `(frame, label_id)` tuple keys.

`AnalysisStage.rehydrate(pipeline_name, m) -> AnalysisResult` reads the
artifact back into an `AnalysisResult` for the Results page or the
Analysis page's overlay code. The `label_masks` arrays come back lazy
when the Zarr path is used (we wrap them in a tiny `LazyZarrArray` that
mirrors `(T, H, W)`-shaped numpy semantics and reads chunks on `[]`);
NPZ-backed reads materialize eagerly since NPZ doesn't support partial
loads cheaply.

### Storage helpers — `storage.py`

Wraps two write paths behind one API:

```python
def write_label_stack(path: Path, labels: np.ndarray) -> str:
    """Write a (T, H, W) int32 label stack. Returns the relative
    artifact path that was actually written ('labels.zarr' or
    'labels.npz'). Picks zarr if available, falls back to npz.
    """

def read_label_stack(path: Path) -> np.ndarray:
    """Read back a label stack from either backing format."""
```

This is the only place that knows the backend choice, so swapping in
xarray or tensorstore later is a one-file change. `zarr` is added to
`requirements.txt` as **optional** in spirit — `import zarr` is guarded;
the rest of the app keeps working without it. We do not depend on
`xarray` at all; the generic doc's xarray usage was nice-to-have for
labeled axes but adds an import that we don't need.

## Wiring into the existing flow

Four touchpoints, all small:

### 1. `MainWindow.__init__` — own a `Session` per active experiment

`MainWindow` already has `self.exp_manager`. Add `self.session:
Optional[Session] = None` and a `_attach_session_for(filepath)` helper.
Called from the Import page after a successful load (see touchpoint 2).
Storage root defaults to `~/.nd2studios/workspace`; overridable via
`ND2STUDIOS_WORKSPACE` env var so the profiling harness can scope to a
tmpdir.

`closeEvent` already drains the job runner; no extra work needed —
`Session` holds nothing that needs explicit teardown (manifest writes
are synchronous).

### 2. `ImportPage._on_confirm` — create/attach the session

After `set_status("imported")`, call
`main_window._attach_session_for(filepath)`. If the workspace already
has a `recipe.json` and/or `analysis/...` committed for this file, push
that data into the active `ND2StudiosRecord` so the user lands on the
Recipe page already populated. The status indicator gains a small
suffix ("Imported — workspace resumed") so the user can tell whether
a warm start happened.

This is also where we **offer** warm-start rather than apply silently:
if a prior commit exists, a single `QMessageBox.question` lets the
user pick "Resume prior recipe / analysis" or "Start fresh." The
"start fresh" path archives the prior session dir to
`<hash>.archived-<timestamp>/` rather than deleting it, so nothing is
lost.

### 3. `RecipePage._on_accept` — commit the recipe stage

Today `_on_accept` appends the trial step to `self._recipe` and sets
status to `preprocessed`. Phase 6 adds: write the committed recipe to
`session.stage("recipe").commit()`. The processed channels stay in
`exp._processed_channels` for the current page — releasing them would
break the right-side viewer immediately. The release happens on
**leaving the Recipe page** (touchpoint 4).

### 4. `MainWindow._navigate` — release on page leave

`_navigate` already saves the outgoing page's state via
`save_to_experiment`. Add: after that, if the outgoing page is `recipe`
and the session has a committed recipe, drop `_processed_channels` to
`None` and remember a sentinel `exp._processed_view = EnhancedDataset(...)`.
The Export, Analysis, and Results pages already read
`exp._processed_channels` — they get a thin shim
`exp.processed_view()` that returns either the live dict or the
EnhancedDataset wrapper, transparent to the caller.

Same idea on leaving `analysis` after a committed run: clear
`exp.analysis_results[<pipeline>][<m>].label_masks` to `None` and stash
a sentinel `_committed=True` so the Results page knows to rehydrate
from disk on demand.

The Recipe/Analysis pages call `rehydrate()` on `on_activated()` when
they need the in-memory copies back, so a user navigating Recipe →
Export → Recipe gets the original behavior. The cost is a one-shot
recipe re-run (cheap on a cache hit; the Phase 3 cache + Phase 5
runner already absorb this) or a one-shot label-mask read (a sequential
Zarr / NPZ read; fast).

### 5. `AnalysisPage._on_finished` — commit the analysis stage

The existing handler stores the `AnalysisResult` into
`exp.analysis_results[pipeline_name][m]`. Add: hand it to
`session.stage("analysis", pipeline_name).commit_m(m, result)`. The
write is per-M so a multi-M run streams to disk incrementally rather
than holding all M positions in RAM until the queue drains. The Phase 5
`PipelineCommitJob` already runs per M; the commit hook fires once per
job completion.

## Acceptance criteria

- [ ] Importing an ND2 file creates
  `~/.nd2studios/workspace/sessions/<hash>/manifest.json` with the
  file's shape, channel names, and pixel size.
- [ ] Accepting a recipe writes `recipe/recipe.json` and records a
  `recipe` `StageRecord` in the manifest with `committed_at` set.
- [ ] Running a full analysis (multi-M) writes a Zarr (or NPZ)
  `labels_<channel>` artifact per M and a `summary.json` per
  pipeline. The Results page reads them back and produces the
  same measurement CSV as before.
- [ ] Leaving the Recipe page after Accept drops
  `exp._processed_channels` to `None`; the Export page and Analysis
  page still work because `processed_view()` returns an
  `EnhancedDataset` that lazily reapplies the recipe.
- [ ] Re-importing the same file in a fresh process detects the
  workspace, prompts "Resume prior recipe / Start fresh"; choosing
  Resume populates the Recipe page with the prior recipe and the
  Results page with the prior measurements without rerunning
  anything.
- [ ] When `zarr` is not installed, every committed artifact uses
  NPZ; the app produces a single-line status note rather than a
  crash.
- [ ] `.nd2s` save/load is unchanged. Loading an old `.nd2s` does not
  fail; if no matching workspace exists, the app behaves exactly as
  in V1.37.
- [ ] Total RSS across the workflow (Import → Recipe accept → Export
  preview → Analysis run → Results compute) does not grow
  monotonically: it dips after each leave-page release, as confirmed
  in `profiling/baselines/phase_06.json`.

## Out of scope for V1.38

- **Materializing `processed.zarr`.** Lazy reapplication is the
  default; materialization is a tunable for a future phase if
  benchmarks show repeated re-derivation cost dominating.
- **Background workspace janitor.** No automatic eviction of old
  workspaces. The user can `rm -r ~/.nd2studios/workspace` to reset.
  A future version can add a Workspace menu with `du` + clear
  operations.
- **Cross-machine workspace portability.** The hash key works on any
  machine but the workspace dir lives on `~`; sharing analysis
  results between two researchers happens via `.nd2s` (already
  works) or by zipping the workspace dir (works but not advertised).
- **Migrating `BatchWorker` to use the workspace.** Batch already
  iterates files and writes its own `batch_results.csv`; converting
  it to write per-file workspaces is a follow-up.
- **Per-stage progress UI.** The status indicator in the title bar
  is fine for V1.38. A dedicated workspace pane is a future polish.

## Risk and rollback

The package is additive. Every existing read path
(`exp._processed_channels`, `exp.analysis_results[...]`) continues to
work when no commit has happened — the release hooks only fire after a
successful `commit()`. Rollback options, smallest first:

- Set `ND2STUDIOS_DISABLE_WORKSPACE=1` in the environment —
  `_attach_session_for` becomes a no-op and the page-leave release
  hooks short-circuit, restoring V1.37 behavior exactly. The env-var
  check is one line in each touchpoint.
- Revert the touchpoints in `import_page.py`, `recipe_page.py`,
  `analysis_page.py`, `main_window.py`, and `experiment_manager.py`.
  The `nd2studios/pipeline/` package becomes dead code, harmless.
- Or revert the whole commit. No `.nd2s` schema change.

No on-disk schema migration for any user-saved file. Existing `.nd2s`
sessions load identically. The new workspace directory is created on
first import; deleting it is safe at any time.

## After this phase

Phase 7 (optional GPU & multi-resolution) can write a `pyramid/` layer
into each session and read it on viewer attach. The `Session` API is
the natural extension point: a `pyramid_stage` joins `recipe_stage` and
`analysis_stage`, and the multi-axis viewer asks the session for the
appropriate level on each frame request.

Verify before moving on:

- A complete workflow (Import → Recipe → Export → Analysis → Results)
  runs end-to-end on a representative ND2 file with the workspace
  populated and RSS not monotonically growing.
- The workspace directory's contents are inspectable and meaningful.
- The application starts up, opens a previously-processed file, offers
  warm-start, and resumes correctly.
