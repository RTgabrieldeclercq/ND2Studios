# V1.46 — Tracking off the GUI thread (fix "not responding" at seg→track)

## Report

The app goes "not responding" during the transition from the end of segmentation
to the beginning of tracking.

## Root cause

During a Run, measurement is already off-thread (`_ResultsMeasureJob` on the
`JobRunner`), but the **object linker ran synchronously on the GUI thread** in two
spots, both reached right at the seg→track boundary:

1. `_on_runner_result` / `_RUN_MEASURE_KEY` — per-M default tracking
   (`link_objects(rows)`) immediately after each multipoint's measurement.
2. `_run_track_objects` — the Track Objects node (`link_objects_with_params`).

The Hungarian linker's cost grows with object count (and SerialTrack far more):
on a dense field of thousands of nuclei this is seconds to minutes, so the Qt
event loop blocked and the window showed as unresponsive.

## Fix

Move both linker calls onto a worker, mirroring how measurement already works.

- **add** `_TrackJob(AnalysisJob)` — runs `link_objects` (params=None, the per-M
  default) or `link_objects_with_params` (a Track Objects node) in the worker;
  mutates rows in place and returns them. Pure numpy/scipy/pandas/numba — no Qt.
- **keys** `_RUN_TRACK_KEY` (per-M default tracking) and `_RUN_TRACKOBJ_KEY`
  (Track Objects node).
- **per-M loop:** `_RUN_MEASURE_KEY` now tags `m_position`, stashes the rows in
  `_run_pending_track_rows`, and submits `_TrackJob(_RUN_TRACK_KEY)`; the
  `_RUN_TRACK_KEY` result accumulates into `_run_all_rows` and calls
  `_advance_run_m`. `_run_pending` stays = the analysis node id across the whole
  M-loop, so the walk is already gated.
- **Track Objects node:** `_run_track_objects` submits `_TrackJob(_RUN_TRACKOBJ_KEY,
  rows, node.params, px)`, stores `_run_trackobj_node`, and sets
  `_run_pending = node.id` (async-node convention). `_finish_track_objects`
  (on the result) publishes rows, refreshes table/plots/overlay, and calls
  `_run_finish_node`.
- **plumbing:** `_on_runner_cancelled` / `_on_runner_progress` key lists include
  the two new keys; `_run_pending_track_rows` / `_run_trackobj_node` initialised in
  `__init__` and reset on cancel.

## Decisions

- *In-place mutation across the hand-off is safe.* The run walk waits for the job
  before touching the rows again; the Track Objects node's rows may also back the
  results-table model, but the linker only **adds** keys (`track_id`,
  `track_length`, `track_validation`) — individually atomic under the GIL — so a
  concurrent repaint sees old-or-new, never corruption. No deep copy (50k dicts).
- *Failures keep the rows.* `link_objects` pre-initialises `track_id=None`, so a
  failed track job still yields usable (untracked) rows; both handlers fall back to
  the stashed rows on `result.ok == False`.
- *Legacy `_RUN_RESULTS_KEY` and the scoped preview-walk tracking* stay on the main
  thread — they operate on a small selected-plane subset, not the whole-file Run,
  so they are not the freeze.

## Verification

- `py_compile` + offscreen import clean; `_TrackJob`, `_run_track_objects`,
  `_finish_track_objects`, both keys present.
- `_TrackJob.run` (params=None and with-params) on synthetic rows produces the
  expected tracks via a real `ProgressReporter`, no Qt.
- State-machine trace: `_run_pending` gates the walk through both the per-M track
  jobs and the Track Objects job; `_advance_run_m` / `_run_finish_node` resume
  correctly; cancel path resets the new state.
