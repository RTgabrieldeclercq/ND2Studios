# V1.46 — Pipeline Run: surface silent analysis-node skips & swallowed job errors

## Problem

A user's saved pipeline (`Cell-Tracker pipeline.nd2s_pipeline.json`:
`input:processed → StarDist Segmentation → Track Objects → Cell-Tracker Spatial
Maps`) "runs but produces no results": the nodes animate shaded→gold→done and the
run finishes, but no segmentation, tracks, or spatial maps appear, and the
`Run: '<pipeline>' done on N multipoint(s) → X objects.` status line — which
`_advance_run_m` emits when the analysis loop completes — **never appears at all**.

That last fact is the key: if the StarDist compute job merely *failed*, the
`_RUN_ANALYSIS_KEY` handler would still call `_advance_run_m()` (pipelines_page.py
~2657), drain the M-queue, and print the "→ 0 objects" line. Its total absence
means `_run_analysis_node` returned early through one of its **guard clauses**
before the per-M loop ever started — and every one of those guards exits by
calling `self._run_finish_node(node.id)` with **no status message, no log line**.
So the node completes, `Track Objects` then reports "no measured objects yet —
skipped", `Spatial Maps` (which also has an empty `templates: []`) finishes blank,
and the user has zero visibility into which precondition failed.

Ruled out during diagnosis: the runtime environment (StarDist loads its pretrained
model and infers on CPU here), pipeline registration (`stardist_segmentation` is
force-imported at `__main__.py:81`), and the graph itself (loads to the correct
5-node / 3-edge DAG with the right execution order; the unwired If/Else node is
correctly unreachable).

## Goal

Make the Run's silent failure modes **observable** — turn every guard bail-out in
`_run_analysis_node`, and the swallowed analysis-job error, into a specific
status-bar message (and a `logging.warning`). This is both the diagnostic that
identifies the user's root cause on their next run **and** a genuine robustness
fix: a Run should never silently do nothing.

## Approach

`nd2studios/pages/pipelines_page.py`:

1. Add `import logging` + a module logger `_log = logging.getLogger(__name__)`.
2. Add a small helper `_skip_analysis_node(node, reason)` that emits
   `self._set_status(f"Run: '{node.title}' skipped — {reason}")`, logs a warning,
   and calls `self._run_finish_node(node.id)`.
3. Replace each silent guard in `_run_analysis_node` with a call to that helper,
   each with a distinct reason:
   - no active record / no resolvable action / no channel names,
   - analysis pipeline `<name>` not registered (`cls is None`),
   - could not read processed channels (`view[nm]` raised — include the exception),
   - processed view has no channels.
4. In `_on_runner_done`'s `_RUN_ANALYSIS_KEY` branch, when the job failed or
   returned `None`, emit a status/log line with `result.error` before advancing
   past that multipoint (instead of the bare `_advance_run_m()`).

Purely additive: control flow and success paths are unchanged; only the
previously-silent exits gain a message.

## Files

- `nd2studios/pages/pipelines_page.py` — logger + `_skip_analysis_node` helper;
  instrument `_run_analysis_node` guards and the `_RUN_ANALYSIS_KEY` failure path.

## Key decisions

- Diagnostics only; no behavioral change to a working run. We do **not** guess at
  a "fix" for the empty result until the surfaced message tells us which
  precondition is actually failing in the user's session.
- Prefer the status bar (user-visible) plus a logged warning (captured by the
  `logging.basicConfig(INFO)` set up at startup) so the reason survives past the
  transient status text.
