# V1.36 — Phase 4: pyqtgraph GPU-Accelerated Display

## Goal

Eliminate the per-frame CPU compositing path (`apply_lut` →
`multiply by RGB color` → `clip to uint8` → `QImage` → `QPixmap`) and
move channel LUT + composition to the GPU via a `pyqtgraph`-backed
canvas. After this phase, dragging a LUT histogram handle, toggling a
channel chip, or changing a channel color is **visually instant**
(< 16 ms), and scrubbing M / T / Z for cached planes does not allocate
or convert an RGB array on the GUI thread.

## Where ND2Studios already stands

The current display path is `MultiAxisViewer._compose_current_frame`:

1. For each enabled channel, pull the raw 2-D plane from `FrameCache`.
2. Call `apply_lut(frame, lo, hi, gamma)` — numpy → uint8 grayscale.
3. Multiply the uint8 grayscale by the channel's `(R, G, B)` tuple
   and accumulate into a float32 `(H, W, 3)` composite.
4. Clip to uint8 → handoff to `ImageCanvas.set_image` → `QImage` →
   `QPixmap` → `QLabel.update()` → `paintEvent` redraws the pixmap.

Every step in 1–4 is per-pixel CPU work. A 2 K × 2 K image with 4
channels costs ≈ 64 MB of `float32` per composite plus ≈ 16 MB of
`uint8` per `apply_lut` call. With Phase 3's cache delivering hits
sub-millisecond, **the composite step is now the dominant cost on the
GUI thread** for LUT drag, channel toggle, and (to a lesser degree)
slider scrub.

The Phase 4 doc's prescription — one `ImageItem` per channel, levels
+ LUT applied on the GPU, additive composition mode — maps cleanly
onto ND2Studios because:

- We already key the cache `(c, m, t, z, z_mode)` per channel, so a
  per-channel render path is a natural fit (no cache-key changes).
- Channel chips and the LUT sidebar are already per-channel widgets;
  their handlers just need to drive `set_channel_visible` /
  `set_channel_levels` instead of triggering a full recompose.
- pyqtgraph 0.14.0 is already pulled in transitively (verified via
  `python -c "import pyqtgraph; print(pyqtgraph.__version__)"`), so
  no new pin is required — we add an explicit entry to keep upgrades
  intentional.

## Approach

### Architectural shape

```
GpuImageCanvas(QWidget)
└── pg.GraphicsLayoutWidget
    └── pg.ViewBox(lockAspect=True, invertY=True)
        ├── pg.ImageItem(ch_0)   ─ LUT + levels, CompositionMode_Plus
        ├── pg.ImageItem(ch_1)   ─ "                                "
        ├── …                                                       
        ├── pg.ImageItem(composite_fallback)  ─ used by set_image(rgb)
        └── OverlayItem (custom QGraphicsItem)  ─ crop / draw / edit
```

Two display paths live on the same canvas:

- **GPU compositing path (new, default).** One `ImageItem` per
  channel. Each owns a colored LUT (black → channel color, 256
  entries) and a `(lo, hi)` levels pair. `CompositionMode_Plus` makes
  Qt's QPainter sum the channels — Qt is the GPU-or-software
  rasterizer here; either way it does the work outside our Python
  loop. The viewer pushes raw uint16/float32 planes via
  `update_channel(c, plane)`; the GPU handles the rest.
- **Composite fallback path.** A single `ImageItem` reserved for
  pre-composed RGB arrays. `set_image(rgb_uint8)` routes there so
  callers that already produce an RGB array (export preview,
  recipe-page intermediate result, post-process hook) keep working
  without changes. The per-channel layers are hidden when the
  fallback is active and vice versa.

### Module placement

```
nd2studios/widgets/gpu_image_canvas.py   # the new canvas
nd2studios/widgets/multi_axis_viewer.py  # gains a GPU code branch
nd2studios/core/settings.py              # USE_GPU_DISPLAY flag
nd2studios/__main__.py                   # pyqtgraph startup config
```

The existing `nd2studios/widgets/image_viewer.py` (`ImageCanvas`,
`ZoomToolbar`, `CHANNEL_COLORS`, the `composite_channels` helper) is
**not removed**. It is still imported by `export_preview_dialog.py`,
`recipe_page.py`, `export_page.py`, `stitch_dialog.py`,
`lut_sidebar.py`, and the embedded `ImageViewer` helper used by
non-multi-axis screens. Phase 4 is scoped to the multi-axis viewer
(the hot path); other screens migrate incrementally in later
versions.

### The viewer's new code branch

`MultiAxisViewer.__init__` picks the canvas type based on
`Settings.USE_GPU_DISPLAY` (and an `ND2_DISABLE_GPU_DISPLAY=1` env
override for emergency fallback without code edits). `_compose_current_frame`
keeps its existing CPU path *only* when the canvas is the legacy
`ImageCanvas`. When the canvas is `GpuImageCanvas`, a new
`_render_current_frame_gpu` is called instead:

1. For every channel chip, set visibility on the GPU canvas
   (`canvas.set_channel_visible(c, on)`).
2. For every *enabled* chip:
   - Read `(lo, hi, gamma)` from the LUT sidebar; pass `(lo, hi)` to
     `canvas.set_channel_levels(c, (lo, hi))`. Gamma is intentionally
     left as a follow-up — pyqtgraph's stock `ImageItem` does linear
     levels only; a non-linear LUT requires generating a 256-entry
     table per (color × gamma) pair. Phase 4 ships with linear levels
     and a gamma-shim TODO. Most McGhee Lab sessions never touch
     gamma.
   - Read the chip's `(R, G, B)` color; pass to
     `canvas.set_channel_color(c, rgb)`. The canvas rebuilds the
     channel's colored LUT in place.
   - Look up the plane in the cache; on hit, call
     `canvas.update_channel(c, plane)`. On miss, defer to the V1.34
     `IOWorker` exactly as today.
3. Pin keys the same way the CPU path does (so the prefetcher cannot
   evict on-screen channels).
4. Trigger prefetch neighbors.

The post-process hook (`set_frame_post_process`) is a CPU-RGB
operation — it stays on the composite-fallback path. When a hook is
attached the viewer falls back to `_compose_current_frame` so the
hook continues to receive a `(H, W, 3) uint8` array.

### Tool parity (crop / draw / edit)

The new canvas must keep emitting the existing signals so the
analysis page and any other consumer of crop/draw/edit do not need
edits:

- `crop_rect_selected(x, y, w, h)`
- `shape_drawn(mode, vertices)`
- `vertex_moved(idx, iy, ix)`, `edit_committed()`
- `clicked(iy, ix)`

The legacy `ImageCanvas` implements these by overriding
`mousePressEvent` / `mouseMoveEvent` / `mouseReleaseEvent` on the
QLabel and painting overlays in `paintEvent`. In pyqtgraph the scene
owns the mouse events and the ViewBox owns pan/zoom. We bridge by:

- Connecting `viewbox.scene().sigMouseClicked` and
  `sigMouseMoved` to the canvas, gated by the active tool mode.
- Adding a single `OverlayItem(QGraphicsItem)` as a child of the
  ViewBox. It owns its own `boundingRect()` (the image rect) and
  paints crop / draw / edit overlays in **scene coordinates** —
  which is what we want, because scene coords are image-pixel coords
  once the `ImageItem` is at unit transform.
- Toggling `viewbox.setMouseEnabled(False, False)` when a tool is
  active so pan/zoom don't fight tool drags. Re-enabled on tool
  exit.

The coordinate transforms (`image_to_widget`, `widget_to_image`) are
re-derived through pyqtgraph: `viewbox.mapSceneToView(QPointF)` and
`viewbox.mapFromView(QPointF)` give us image-pixel ↔ widget mappings
without us writing them.

### Pan / zoom toolbar

`ZoomToolbar` calls `canvas.reset_zoom()`, `zoom_in()`, `zoom_out()`,
and `set_pan_mode(on)`. We implement those on `GpuImageCanvas` by:

- `reset_zoom` → `viewbox.autoRange()` + emit `zoom_changed(1.0)`.
- `zoom_in` / `zoom_out` → `viewbox.scaleBy((0.77, 0.77))` /
  `(1.3, 1.3)` and emit the new fractional zoom via `_emit_zoom()`.
- `set_pan_mode(on)` → flips `viewbox` left-button mode between
  `RectMode` (off, default) and `PanMode` (on). The `clicked`
  signal is suppressed while pan is on, mirroring legacy behavior.

### Feature flag and fallback

`Settings.USE_GPU_DISPLAY = True` is the default. We honor an env
override `ND2_DISABLE_GPU_DISPLAY=1` (read once at canvas-construction
time) so a user on a machine with a flaky GL driver can fall back
without an editor. The decision is made per-`MultiAxisViewer` so a
single instance can be downgraded if construction raises.

Construction is defensive: if `import pyqtgraph` or
`GpuImageCanvas()` raises (driver missing, headless display, etc.),
the viewer falls back to the legacy `ImageCanvas` and logs once. No
end-of-the-world.

### Startup wiring

`__main__._setup_environment` adds:

```python
import pyqtgraph as pg
pg.setConfigOptions(imageAxisOrder="row-major", useOpenGL=False,
                    antialias=False, background=Settings.BG_SECONDARY)
```

`useOpenGL=False` is the safe default — the Phase 4 doc explicitly
notes OpenGL has driver-compat issues on Linux/Windows in
remote-desktop sessions. The McGhee Lab's main workstation runs
locally and could enable it later; the cost of leaving it off is
small because Qt's raster path is already very fast for our texture
sizes.

## Acceptance criteria

- [ ] Toggling a channel chip is visibly instant (no full recompose;
  the chip handler calls `canvas.set_channel_visible` only).
- [ ] Dragging a LUT histogram handle updates the image at 60 FPS;
  the handler calls `canvas.set_channel_levels` only.
- [ ] Scrubbing M / T / Z over cached planes does not allocate an
  `(H, W, 3) uint8` composite anywhere on the GUI thread (verified
  by a `tracemalloc` snapshot diff around a scrub gesture).
- [ ] Tool signals (`crop_rect_selected`, `shape_drawn`,
  `vertex_moved`, `edit_committed`, `clicked`) still fire from the
  GPU canvas and reach the analysis page unchanged.
- [ ] Pan / zoom toolbar buttons still work; zoom percentage label
  updates.
- [ ] When the post-process hook is set, the canvas falls back to
  the composite path and the hook receives an `(H, W, 3) uint8`
  array (no regressions for `set_frame_post_process` users).
- [ ] Setting `ND2_DISABLE_GPU_DISPLAY=1` and re-launching produces
  the legacy `ImageCanvas` and the app remains fully functional.
- [ ] No CPU-side `apply_lut` or RGB compositing call is on the
  GPU path's hot loop (verified by reading
  `_render_current_frame_gpu`).

## Out of scope for V1.36

- Gamma application on the GPU. Linear levels only; gamma is a
  follow-up that needs per-(color, gamma) LUT regeneration. Until
  then, gamma defaults to 1.0 in the sidebar and any non-default
  gamma is silently ignored on the GPU path.
- Porting `export_preview_dialog`, the embedded `ImageViewer`,
  `recipe_page`, etc. to the GPU canvas. They keep using
  `ImageCanvas`. The hot path (multi-axis viewer) is where the win
  is.
- A `useOpenGL=True` mode. We will revisit once we have a baseline.

## Risk and rollback

The legacy CPU path is preserved verbatim. The new branch is gated
on `Settings.USE_GPU_DISPLAY` and the `ND2_DISABLE_GPU_DISPLAY` env
var. If a session-blocking bug appears, the rollback is one of:

- Flip `Settings.USE_GPU_DISPLAY` to `False`.
- Set `ND2_DISABLE_GPU_DISPLAY=1`.
- Revert this commit.

No data on disk changes; no `.nd2s` schema migration; no recipe
format change.

## After this phase

Phase 5 (background analysis with cancellation) is the next
non-trivial win. The mask/spot results it produces will land in the
new `OverlayItem` and `ScatterPlotItem` slots already present on
`GpuImageCanvas`, so Phase 5 won't have to redesign the canvas.
