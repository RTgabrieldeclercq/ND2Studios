# V1.34 — Phase 2: Lazy Loading & Threading

## Goal

Close the residual GUI freezes on M / T / Z scrubbing by moving the
last on-thread read off the GUI thread, and grow the in-memory frame
cache to actually use the RAM the user has spare. After this phase, the
viewer never calls a synchronous `volume.get_frame()` from a Qt slot,
and `FrameCache` is sized adaptively to the machine.

## Where ND2Studios already stands

Most of what the framework-agnostic Phase 2 doc proposes ND2Studios
*already has* — Phase 1 confirmed it via the profiling harness. Before
adding anything, we audit what exists.

| Phase 2 doc concept                          | Existing ND2Studios equivalent                                                       |
| -------------------------------------------- | ------------------------------------------------------------------------------------ |
| Lazy 6D Dask array per file                  | `LazyND2Volume` (uses `nd2.ND2File.to_dask()`) + `LazyMultiFileND2Volume` (V1.28)    |
| Per-format reader behind a uniform interface | `LazyND2Volume` / `LazyMultiFileTIFFVolume` already match method-for-method          |
| Plane-fetch API                              | `volume.get_frame(c, m, t, z, z_mode, z_start, z_end) -> (H, W) ndarray`             |
| Open file in worker, not GUI thread          | `LoadWorker(BaseWorker)` (V1.0) — emits `finished(result)` with the volume          |
| `IOWorker` on a `QThread` for plane requests | `PrefetchManager(QThread)` (V1.17) — does *speculative* reads off the GUI thread     |
| Cache of returned planes                     | `FrameCache` (V1.17) — thread-safe LRU keyed by `(c, m, t, z, z_mode)`               |
| Cancellation / progress / error signals      | `BaseWorker` exposes `progress`, `status`, `finished`, `error`, `cancel()`           |
| Clean shutdown                               | `BaseWorker._running` registry keeps a Python ref per running thread                 |

That leaves **three** gaps. Phase 2 for ND2Studios is exactly these.

### Gap 1 — synchronous reads still happen on the GUI thread

[`MultiAxisViewer._compose_current_frame`](../../nd2studios/widgets/multi_axis_viewer.py)
checks `FrameCache.get(key)` first; on a miss it calls
`self._volume.get_frame(...)` *inline*, which reads from disk and
decodes a Z stack on the Qt thread. The prefetcher only helps for the
neighbors of the *previous* coords — every fresh slider movement
incurs `n_channels` synchronous reads before the redraw can finish.
This is the residual freeze Phase 1 baselines showed up on scrub.

### Gap 2 — `FrameCache` ignores how much RAM the machine has

`FrameCache(max_bytes=300 * 1024 ** 2)` is hard-coded everywhere. The
`00_README.md` for this initiative is explicit: trade RAM for speed.
A laptop with 8 GB free and a workstation with 200 GB free deserve
very different cache budgets. Today they get 300 MB either way.

### Gap 3 — no shared resource-detection helper

The Phase 2 doc and later phases (3, 5, 6, 7) all need a single source
of truth for "available RAM" and "physical core count". Without it,
each subsystem will hand-roll its own `psutil` calls and they will
drift.

## Approach

1. **Add `nd2studios/utils/resources.py`** — Qt-free, mirrors the Phase
   2 doc's spec. `SystemResources` dataclass + `detect()` +
   `recommended_cache_budget_bytes()` + `recommended_worker_count()`.
   Matches the [`nd2studios.utils.profiling`](../../nd2studios/utils/profiling.py)
   precedent (backend-pure, no PySide6).

2. **Add `nd2studios/utils/threading.py`** — `IOWorker(QThread)` that
   services *foreground* (priority 0) frame requests for the viewer.
   One worker per file. Holds its own `volume.reopen()` handle (the
   nd2 library's per-file state is not thread-safe; see
   `LazyND2Channel.materialize`'s docstring). API is intentionally
   small and matches the Phase 2 doc almost verbatim:
   `submit(PlaneRequest) → frame_ready(request_id, key, ndarray) | error(request_id, msg)`.
   The `request_id` is the slider-debounce identifier so the viewer
   can drop stale results that arrive after the user has moved on.

3. **Refactor `MultiAxisViewer._compose_current_frame`** so cache
   misses **enqueue** an `IOWorker` request and the viewer redraws on
   `frame_ready` instead of reading inline. Until every enabled
   channel's plane is in the cache, the viewer either re-uses the
   previously-displayed composite (no flicker) or paints the partial
   composite over the ones that *are* cached. The existing
   `PrefetchManager` keeps running unchanged for ±5 T neighbors.

4. **Wire `FrameCache.max_bytes` to
   `resources.recommended_cache_budget_bytes(reserve_fraction=0.6)`**
   at viewer construction. The 0.6 reserve gives 40% of *available*
   RAM to the frame cache — generous on a workstation (10s of GB), and
   well-behaved on a laptop with 4 GB free (≈ 1.6 GB cache vs the old
   300 MB hard cap). Subsystems added in Phase 3+ will share the same
   `resources` helper.

5. **Profile after the change.** Re-run
   `python -m profiling.harness.run_all phase_02_lazy_loading` and
   compare against `phase_00_baseline.json` from V1.33.

## Architectural decisions

1. **Two threads per dataset, not one.** Phase 2 doc warns about seek
   contention from multiple IO threads on the same file. ND2Studios
   accepts the trade-off: foreground (`IOWorker`) and background
   (`PrefetchManager`) are different priorities and naturally serialize
   at the OS readahead layer. The alternative — collapsing both into a
   single thread with priority lanes — would mean rewriting the
   already-shipped `PrefetchManager` queue. We pick the smaller
   diff.

2. **One handle per thread, always.** Both workers obtain their own
   handle via the existing `LazyND2Volume.reopen()` / `LazyMultiFileND2Volume.reopen()`
   / `LazyMultiFileTIFFVolume.reopen()` factories. This is the same
   convention the prefetcher already uses; we extend it to the new
   `IOWorker`.

3. **Request IDs, not coord-equality.** The viewer increments a
   monotonic counter on every slider event and treats `frame_ready`
   results with stale IDs as discardable. This matches the Phase 2
   doc's snippet and is more robust than coord-equality (which
   wedges if the user re-visits the same coords during fast scrubbing).

4. **Cache budget computed once per viewer instance, at construction
   time.** Re-querying `psutil.virtual_memory()` on every read would
   churn `FrameCache.max_bytes` and make eviction non-deterministic.
   If the user opens a new file the budget is intentionally not
   re-queried — they would have to restart the app to pick up a
   different free-RAM ceiling. Acceptable; this is a desktop GUI.

5. **`utils/resources.py` is backend-pure.** No PySide6 import. Matches
   `utils/profiling.py`. The CLAUDE.md backend-purity rule is honored.
   `utils/threading.py` *does* import PySide6 (it has to — `IOWorker`
   is a `QThread`) but is consciously called out as the boundary.

## What does *not* change

- The `LoadWorker` keeps doing the cold-open + per-channel proxy build
  on its own thread (already correct).
- The `PrefetchManager` queue, signals, and ±5 T neighbor policy stay
  exactly as-is.
- `LazyND2Volume.get_frame` / `LazyMultiFileND2Volume.get_frame` /
  `LazyMultiFileTIFFVolume.get_frame` keep the same contract: synchronous,
  return `(H, W)` ndarray, called from one thread per handle.
- The Phase 2 doc's framework-agnostic `Dataset` 6-D abstraction is
  *not* introduced — ND2Studios's `LazyND2Volume` and the channel
  proxies already cover the same surface, and changing every consumer
  to a new abstraction is gratuitous churn for no profile-driven win.
- TIFF reading does *not* switch to `tifffile.imread(aszarr=True)`.
  The existing per-page direct-read path already gives O(1) per-frame
  cost on the multi-Z hyperstacks the lab uses. We will revisit if
  Phase 1 baselines flag TIFF scrubbing as slow.
- The Phase 2 doc's "delete the now-dead code" note doesn't apply:
  no old read path is being parallel-wired here. The synchronous read
  in `_compose_current_frame` is **replaced**, not duplicated.

## Acceptance criteria

- [ ] On a multi-channel ND2, dragging T at 30 fps does not freeze the
      UI — the IO worker satisfies misses while the GUI thread continues
      to repaint. The displayed frame may lag by one composite, but
      input remains responsive.
- [ ] `FrameCache` budget on a 32 GB machine with 16 GB free comes out
      to ≈ 6.4 GB (40% of available) rather than 300 MB.
- [ ] `nd2studios.utils.resources` imports cleanly with no PySide6
      available (verified via a Qt-free Python shell).
- [ ] `python -m profiling.harness.run_all phase_02_lazy_loading`
      runs end-to-end and emits a snapshot whose `scenario_scrub`
      per-frame ms numbers are lower than `phase_00_baseline.json`
      collected in V1.33.
- [ ] Opening a new file cleanly stops both the previous `IOWorker`
      and the previous `PrefetchManager` before starting the new ones
      (no thread leaks; no zombie handles).
- [ ] No regression in features that exercise `MultiAxisViewer`:
      import preview, recipe page playback, manual mask draw,
      crop selection, vertex edit, post-process hook,
      tile-layout sidebar.

## Common pitfalls (called out for ND2Studios specifically)

- **`nd2.ND2File` is not thread-safe**: every worker MUST hold its own
  handle via `volume.reopen()`. The existing `PrefetchManager`
  already enforces this through a `reader_factory` callable; the new
  `IOWorker` follows the same pattern.
- **Stale results**: by the time `IOWorker.frame_ready` arrives the user
  may have moved the slider three more steps. The viewer compares the
  arriving `request_id` against `self._latest_request_id` and drops
  anything older. Coord-equality would also work for forward scrubbing
  but breaks when the user revisits coords mid-flight.
- **`_normalize_to_2d`** is currently called on the GUI thread inside
  `_compose_current_frame`. After Phase 2 it runs on the IO worker
  thread — cheap operation, but it does mean the worker emits `(H, W)`
  ndarrays already normalized. The Phase 2 doc's `IOWorker` does not
  normalize; we extend ours to do so to keep the GUI slot trivial.
- **Cache budget on huge files**: even with 40% of free RAM, a single
  4096×4096 16-bit frame is 32 MB. 6.4 GB still holds ~200 such frames.
  Good enough for ±5 T neighbors × 16 channels × 2 M positions — fine
  for the McGhee Lab's usual files. If a session blows the budget,
  the existing LRU eviction handles it.
- **Profiling harness counts**: the scrub scenario calls
  `volume.get_frame()` directly, bypassing the viewer entirely. Phase
  2 does not speed *that* number up — the win is in `scenario_tab_switch`
  and (eventually) a new GUI-driven scrub scenario. The Phase 2
  doc's biggest claim ("opening a multi-GB file returns control to
  the GUI within 1 second") was already true for ND2Studios in V1.0
  because the cold open happens inside `LoadWorker`. We are honest
  about that in the post-phase numbers.

## After this phase

Phase 3 (Frame Cache & Prefetcher) is largely done already
(`FrameCache` + `PrefetchManager`). The next non-trivial win is
Phase 4 (pyqtgraph display) — the current `ImageCanvas` rebuilds a
`QImage` from a uint8 RGB ndarray every frame; pyqtgraph would push
that to the GPU and make LUT/contrast changes free. Phase 2's
`IOWorker` is a precondition: pyqtgraph is fast enough to make the
synchronous read path the new bottleneck if we don't fix it first.
